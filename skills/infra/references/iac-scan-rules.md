# iac-scan の規則と、構成コードの変更の止め方

> **3 行でわかる要約**
> 1. scripts/iac-scan.sh が Terraform の構成コードで落とす 12 の規則と、例外の書き方をまとめた資料です。
> 2. 規則ごとに番号・重さ・直し方を出し、変数は既定値と全環境の値で確かめます。
> 3. 構成コードを書く前と、FAIL を直すときに開いてください。

## 規則の一覧

この節は、規則の番号・重さ・名前・直し方の表です。同じ表は `iac-scan.sh --rules` でも出せます。

| 番号 | 重さ | 名前 | 直し方 |
|---|---|---|---|
| IAC-001 | CRITICAL | 外から読める保存先 | ACL を private にし、方針の誰にでもの Allow を消す |
| IAC-002 | HIGH | 公開のブロック | バケットごとに公開のブロックの 4 項目を true にする |
| IAC-003 | HIGH | 権限の「*」 | 操作と対象を名指しする |
| IAC-004 | CRITICAL | 管理の口の全開 | 0.0.0.0/0 から 22・3389・5432 などを開けない |
| IAC-005 | HIGH | 暗号化の無い保存 | データベースと保存の領域、バケットを暗号化する |
| IAC-006 | CRITICAL | 外から届くデータベース | publicly_accessible を false にする |
| IAC-007 | HIGH | 削除の保護 | deletion_protection を true、最後の複製を取る |
| IAC-008 | HIGH | バックアップの保持 | 保持を 7 日以上にする |
| IAC-009 | HIGH | 監査ログの無効 | CloudTrail を置き、全地域と改ざんの検知を入れる |
| IAC-010 | MEDIUM | 版の管理の無いバケット | 版の管理を Enabled にする |
| IAC-011 | CRITICAL | コードに書いた秘密 | 値を消して保管庫から参照し、漏れた値は作り直す |
| IAC-012 | HIGH | 平文の通信 | ロードバランサーは HTTPS、配信は HTTPS へ寄せる |

## 変数と環境

この節は、変数の値の確かめ方です。iac-scan は init も適用もせず、ファイルだけを読みます。

`var.<名前>` は、変数の既定値と、ディレクトリの下の全 *.tfvars の値で確かめます。どれか 1 つの環境で穴になれば落とします。値に解けないときは WARN を出し、判定を人に戻します。

| 場合 | 扱い |
|---|---|
| 値が書いてある | その値で確かめる |
| 変数で、既定値か tfvars がある | 全部の値で確かめ、1 つでも穴なら FAIL |
| 値に解けない | WARN を出す |

## 例外の書き方

この節は、規則を外すときの決まりです。外すのは、AWS の仕様で絞れないときだけにします。

番号の規則のほかに、iac-scan は「境界の外」も落とします。権限の境界を付けた役割の方針に、境界の外の操作があるときです。AWS は方針に書いた操作でも拒むので、棚卸しのような守りが毎回黙って落ちます。境界に足すか、方針から外します。

行か直前の行に `# iac-scan:allow IAC-003 <理由>` と書きます。理由の無い例外は「例外の理由」で FAIL です。例外の数は設計書の IAM の節にも書き、レビューで数を見ます。

| 例外にしてよい例 | 理由 |
|---|---|
| ecr:GetAuthorizationToken の対象 | AWS の仕様で対象を絞れない |
| 鍵の方針の対象 | 鍵の方針の「*」は、その鍵だけを指す。iac-scan は鍵の方針を見ない |

## 計画の差分で止める

この節は、構成コードの変更を適用の前に止める条件です。IaC（インフラをコードで作る仕組み）の変更は、CI が計画を出してから人が承認します。

| 計画に出たもの | 動き |
|---|---|
| 許す物の一覧にある型の、一覧にある属性の変更だけ | 変更記録に写し、承認を待つ。適用は承認 1 人の環境と適用の役割（ROUTE: apply） |
| 一覧に無い型、一覧に無い属性、新しく作る資源、構成にある provisioner（local-exec など） | 承認 2 人の環境（<環境>-guarded）と守りの適用の役割でだけ適用する（ROUTE: guarded） |
| 置き換えか削除が 1 件以上 | 止めて、差分を取りまとめ役に渡す。データを持つ資源なら復元の手順も添える |
| データを消す変更（保持の日数を縮める、削除の保護を外す） | どの経路でも通さず止める |
| 一覧の外の部品（プロバイダ） | 止める。計画のときにコードが動くため |
| 前提の検査（check ブロック）の不成立 | 止めて、直してから計画を出し直す |

判定は `scripts/plan-gate.sh <terraform show -json の出力> [--attested <file>]` が行い、終了コードは apply が 0、guarded が 3、止めるが 1 です。

守りは「許す物の一覧」で書きます。止める物を並べる書き方では、並べ忘れた型が承認 1 人で通るからです。一覧は infra_check.py の APPLY_ALLOW で、型ごとに変えてよい属性を並べます。見本の一覧に載るのは、サービスの数と版と、API のイメージのダイジェストと、待ち先の設定です。データベースは、大きさの変更も載せません。rds:ModifyDBInstance は、パスワードや公開の設定も同じ 1 回の操作で変えます。ただ、この操作に効く IAM の条件キーは rds:ManageMasterUserPassword だけで、大きさだけには絞れないからです。

ECS の作業の定義は、置き換えでも止めません。ただし承認 1 人で通すには、2 つの条件があります。1 つ目は、決めた family（API）でダイジェストだけが変わることです。2 つ目は、そのダイジェストが --attested の一覧にあることです。--attested には、CI が来歴の署名を確かめたダイジェストを並べます。来歴とは、どの commit をどの workflow が作ったかの記録です。

守りの経路は、CI の手順だけでなく AWS の側でも強制します。適用の役割の方針は一覧と同じ操作だけにし、データへ届く操作は SCP が名指しの役割のほかに拒みます。CI は判定の前に `plan-gate.sh --selftest` を回し、PASS でなければ止めます。

## ほかの検査との関係

この節は、外の道具との分担です。trivy（構成にある既知の穴を探す道具）は全体の検証で回り、iac-scan は会社の決まりを番号つきで落とします。

| 検査 | 見るもの | 回る所 |
|---|---|---|
| iac-scan | 会社の 12 の規則と、全環境の値 | スキルの evals と、構成コードの直後 |
| trivy | 外の既知の穴の一覧（HIGH 以上で FAIL） | tools/verify-all.sh --full |
| terraform fmt -check | 書式 | 構成コードの直後 |
| plan-gate | 計画の置き換え・削除・前提の検査と、守りの差分の経路 | CI の計画の直後と、スキルの evals |
| deps-diff | lock の file の部品の一覧（SBOM）の差分と、危ない取り込みの形 | PR ごとの必須の検査と、スキルの evals |
