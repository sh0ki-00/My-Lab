# PR の型と、節ごとの根拠

> **3 行でわかる要約**
> 1. PR（プルリクエスト。差分をレビューしてもらう依頼）の文は、差分を読まなくても何を・なぜ・どう確かめたかが分かるように書きます。
> 2. 型の土台は 3 つです。Google のコードレビューの指針、Kubernetes の PR の型、Conventional Commits です。節ごとの根拠は表にしました。
> 3. 書くときは `templates/pr-template.md` を使い、`scripts/pr-check.sh` で機械の検査を通します。

## 1. なぜ本文に書くのか

差分には「何を変えたか」しかありません。なぜその案を選び何を却下したか、どう確かめたか、何に影響するかは、差分の外にあります。PR の文は何年も後に何百人もが読む記録になるので、リンク先が消えても読めるように要点を本文に書きます。

| 読み手 | PR 文から知りたいこと |
|---|---|
| レビュアー | 何を・なぜ・どこを重点的に見るか・どう確かめたか |
| リリースの担当 | 出し方、見る指標、止める基準、戻し方 |
| 1 年後の保守の担当 | なぜこの作りにしたか、何を却下したか |

## 2. 節の順と根拠

節は、読み手が最初の判断に要るものから並べます。

| 節 | 書くこと | 根拠 |
|---|---|---|
| 題名 | `fix:` や `feat:` の型と、何をするかを命令の形で。60 字以内 | Conventional Commits の型。Google（1 行目は何をするかの短い要約） |
| 3 行の要約 | 何を変えたか、なぜか、レビュアーにしてほしいこと | 読み手が最初の判断に要るもの |
| 背景と目的 | 関連 Issue（`Closes #番号`）と困りごとの要点。リンク先が消えても読めるよう、要点を本文に書く | Google（リンクが将来見えなくなる前提で文脈を書く） |
| 変えたこと | 場所・変更・理由の表。構造が変わるなら前後の図 | 差分だけでは理由が分からない |
| 方針 | 採用した案と、却下した案と理由 | Google（なぜこの方法が良いか、既知の弱点を書く） |
| 影響 | 利用者・既存のデータ・性能・セキュリティ・互換・他のチーム | 読み手が、自分への影響を探さずに済む |
| 検証 | 実行したコマンドと結果の抜粋。実行した事実だけ | 推測の「動くはず」を残さない |
| レビューの観点 | 重点的に見てほしい所と、読む順 | Kubernetes（レビュアーへの特記） |
| リリースと戻し方 | 出し方、見る指標、止める基準、戻す手順 | 戻せない変更を混ぜない |
| 用語 | 初出の専門語の言い換え | 新人でも読める |

## 3. 大きさ

1 つの PR は 1 つの目的に絞ります。Google は、100 行ほどを妥当、1,000 行を大きすぎとし、整理のための変更は別の PR に分けるよう勧めています。`pr-check.sh` は `--diff-lines` で差分の行数を受け取り、400 行を超えると分割を促します。

## 4. 書かないこと

「AI が書いた範囲」の節は書きません（社長の指示）。実行していない検証、推測の語、却下した案の無い方針も書きません。
