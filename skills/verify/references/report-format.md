# 完了報告の型

> **3 行でわかる要約**
> 1. 完了報告は、受け入れ条件 1 件ごとに「確認コマンドと結果」を対にして書く文書で、`.company/rules/evidence-and-safety.md` の証拠の決まりを形にしたものです。
> 2. 必須は、3 行の要約・「配るコードの変更」の欄・受け入れ条件の表・直したことの表・未確認の表・検証の記録への参照の 6 つです。配るコードを変えた報告は、先頭に攻撃の結果の節を足します。
> 3. 書いたら `scripts/report-check.sh` を --base 付きで通し、別コンテキストの読み手テスト（My-Lab では `editor`）を受けてから依頼者に出します。

## 1. 必須の節

依頼者は報告を 1 分で判断します。最初の 10 行で「何が終わり、何が終わっていないか」が分かるように、要約と表を先に置きます。

| 節 | 中身 | 検査（report-check.sh） |
|---|---|---|
| 表題 | `# 完了報告: <件名>` | 表題が「完了報告:」で始まる |
| 3 行の要約 | 何の作業か、結果（全体 PASS か、未確認の数）、依頼者にしてほしいこと | 引用ブロックに 3 行 |
| 項目の表 | 「配るコードの変更」の欄に「あり」か「なし」と、配るコードのファイルの数と置き場 | 欄は要約の直下に 1 つで、値が「あり」か「なし」で始まる。欄の無い古い報告は WARN を 1 行出して通す（--base で差分に配るコードがあれば FAIL） |
| 攻撃の結果（「あり」のときだけ） | スクリプトが書いた RESULT の行、手口ごとの表、見つけた脆弱性の表、確かめたことの表。最初の節に置く | 3 節のとおり |
| 受け入れ条件 | 列は「#」「条件」「確認コマンド」「結果」。結果は実行して出た値の抜粋 | 表があり、全行の結果が空でない |
| 直したこと | 列は「場所」「何を」「なぜ」。検証の FAIL を直した記録 | 表がある（無ければ「無し」と 1 行） |
| 未確認 | 列は「条件」「理由」「確かめ方」。確かめられなかった条件を黙って「充足」にしない | 節があり、各行に理由がある |
| 検証の記録 | `docs/verify/<日付>.md`（他のプロジェクトでは `tmp/.verify/last-fast.txt` か `tmp/.verify/last-full.txt`）への参照 | 参照がある |

テンプレートの `<…>` は、文書のどこに残っても FAIL です。コードと HTML の注釈の中は見ません。

## 2. 書いてはいけない言い方

実行していないことを、実行したように書く言い方を禁止します。推測の語は、検査が落とします。

| 言い方 | 理由 | 代わり |
|---|---|---|
| 動くはず、通るはず | 実行していない | 実行し、結果を書く。できないなら未確認に |
| と思われる、おそらく | 推測 | 確かめ方を書き、未確認に |
| 確認済み（コマンド無し） | 何を見たか分からない | 確認コマンドと結果の抜粋 |
| 問題なし | 何を見たか分からない | 見た項目と、出た値 |

## 3. 配るコードの変更と攻撃の結果

配るコード（アプリとして動くコード）を変えた報告は、攻撃の結果を先頭に載せないと出せません。攻撃を送るのは、セキュリティのスキルのスクリプト attack-run.sh（新規。まだ無い）です。節と攻撃の記録はそのスクリプトが書き、人も AI も手で書かず、直しもしません。

### 3.1 配るコードの決め方

配るコードかどうかは、git の差分のファイルを 1 本ずつ次の表に当てて決めます。どの行にも当たらないファイルが 1 本でもあれば「あり」で、迷うファイルも「あり」に倒れます。

| 外すファイル | 見分け方 |
|---|---|
| 置き場 | tmp/ と docs/ の下 |
| 文書 | 拡張子が .md・.mdc・.markdown・.txt・.rst・.adoc のファイル。拡張子の無い LICENSE・NOTICE・CHANGELOG など |
| テスト | test・tests・`__tests__`・spec・specs・e2e・evals のディレクトリの下。名が `test_*.py`・`*_test.*`・`*.test.*`・`*.spec.*`・`*Test.php` のファイル |
| My-Lab の一式 | My-Lab のリポジトリでだけ外す。skills/・tools/・hooks/・router/・.company/・.claude/・.cursor/・.github/ の下と、deploy.sh・install.sh・package.json・package-lock.json・node_modules |

My-Lab の一式を変えたときは「なし」で、攻撃の代わりに、受け入れ条件へ `tools/verify-all.sh` の --full の結果を書きます。My-Lab の samples/ はアプリのサンプルなので、変えたら「あり」です。

差分は、基点から作業ツリーまでの変更です。commit 済み・index・未 commit の変更と、追跡外の新しいファイルを数え、.gitignore で外したファイルは数えません。基点は作業を始めた commit で、例えば git merge-base HEAD main の値です。差分のうち配るコードのファイルは、`bash skills/verify/scripts/report-check.sh --deploy-code <基点>` で出ます。

### 3.2 欄と report-check

欄は 1 つだけにし、要約の直下にある項目の表で、見出しでない行に置きます。report-check が欄の値ごとに求めることは次の表のとおりで、--base を付けると git の差分とも照らします。

| 欄 | --base なし | --base あり |
|---|---|---|
| あり | 3.3 節の攻撃の結果の節。攻撃の記録は形だけを見て、照らしていないことを WARN で知らせる | 3.3 節に加えて、3.4 節の対象の版と攻撃の記録を、今のリポジトリと照らす |
| なし | 攻撃の結果の節か RESULT の行が残っていれば FAIL。差分と照らしていないことを WARN で知らせる | 差分に配るコードがあれば FAIL |
| 欄が無い | 欄を足す前の古い型として、WARN を 1 行出して通す | 差分に配るコードがあれば FAIL。無ければ WARN を 1 行 |
| 置き場・名・値の誤り | 見出しの行や注釈の中の欄、2 つ目の欄、「配るコード変更」のような名、「未定」のような値は FAIL | 同じ |
| 差分を読めない | なし | WARN。基点とリポジトリを確かめて回し直す |

門の検査（gate-check）は、この判定を report-check の --attack-only で受け取ります。そのため 2 つの検査は、同じ報告に同じ判定を出します（`skills/secretary/references/gatekeeping.md` の 3 節）。

### 3.3 攻撃の結果の節

節には、RESULT の行と 3 つの表（手口ごと・見つけた脆弱性・確かめたこと）を、この順に並べます。スクリプトは数をそろえて書くので、report-check は数の食い違いを、手で直した跡として落とします。

| 部分 | report-check が求めること |
|---|---|
| RESULT の行 | 文書の中に 1 本だけで、判定が PASS。入口は全部（52/52 のように両方が同じ）で、未実施 0。新しい脆弱性があれば「→ 再攻撃 0」 |
| 手口ごとの表 | 結果の列は「守れた」「脆弱性 n 件。直して 0 件」「脆弱性 n 件。前からある」「対象外。理由」のどれかで始まる。送った本数の合計が、RESULT のリクエストの本数と同じ。脆弱性の件数の合計が、RESULT の脆弱性と前からある脆弱性の和と同じ |
| 見つけた脆弱性の表 | 行の数が、RESULT の脆弱性と前からある脆弱性の和と同じ。重さは `skills/security/scripts/cvss4.sh` で出す |
| 前からある脆弱性 | 1 件以上なら、脆弱性の表に件数と重さを出し、「前からある脆弱性 n 件を直す承認をお願いします。」の 1 行を置く |
| 確かめたことの表 | 下の表の 8 行がそろい、値が空でなく、`<…>` が残っていない |

確かめたことの表は、攻撃が本物だった証拠です。行ごとの中身と、report-check が落とすものは次の表のとおりです。

| 行 | 中身 | report-check が落とすもの |
|---|---|---|
| 対象の版 | 攻撃したコードの版（3.4 節） | 形が違う。--base では、今の版と違う |
| 届いた本数 | 攻撃用に立てたアプリのログの行数と、送った本数 | どちらかが、RESULT のリクエストの本数と違う |
| 宛先 | スクリプトが送った宛先と、アプリが外へつなごうとして断った接続の数 | 127.0.0.1 の外の IP や名前がある。外へのリクエストが 0 本と書いていない |
| 接続先 | アプリがつなぐ DB・メール・外部 API が、手元か作り物か | 値が空 |
| 許可 | 常設の RoE と、承認記録の番号 | 常設の RoE か A-番号が無い |
| 検出力 | 脆弱性を仕込んだサンプルで、仕込んだ数と見つけた数 | 2 つの数が違う |
| 確かめていないこと | 表に無い手口と、試していない悪用のシナリオ | 空か、「無し」「なし」「-」だけ |
| 攻撃の記録 | スクリプトが書いた記録のパスと、その sha256 の先頭 12 桁 | パスか指紋が無い。--base では、記録が無い、指紋が違う、記録に RESULT の行か対象の版が無い |

「確かめていないこと」は、脆弱性が 0 件でも必ず書きます。スクリプトが試すのは表にある手口だけなので、0 件を安全の印として読ませないためです。

RESULT の行を PASS にできるのは、入口の漏れ 0、未実施 0、新しい脆弱性が再攻撃で 0 件のときです。前からある脆弱性は、件数と重さを出して直す承認を伺えば、PASS のまま出せます。新しい脆弱性は、直して全部の攻撃を送り直します。

攻撃を回せないときは、節に「攻撃は未実施」と理由を書きます。スクリプトがまだ無いときや、アプリを手元で起こせないとき、常設の RoE に署名が無いときです。report-check と門は FAIL のままにし、検査は緩めません。取りまとめ役が依頼者に、未実施のまま進めるかを 1 行で伺います。

### 3.4 対象の版と攻撃の記録

commit の前に攻撃するので、対象の版は、commit と配るコードの未 commit の差分の組で示します。書き方は次の形で、`bash skills/verify/scripts/report-check.sh --target-version` の出力をそのまま使います。

```text
commit 3f2a91c0d4e1、配るコードの差分 5 ファイル（sha256 の先頭 12 桁 9c1e0b7a2f45）
```

差分のハッシュ値は、配るコードの未 commit のファイルを、パスの順に並べて計算します。攻撃のあとで配るコードを直したら、版が変わるので攻撃を回し直します。報告や文書を書き足しても、版は変わりません。

攻撃の記録は、スクリプトが送った要求ごとの宛先・状態番号・長さ・所要時間を残したファイルです。本文とトークン（ログインの証の文字列）は残さず、置き場は tmp/.verify/ の下です。記録は UTF-8 の文字のファイルにし、報告の RESULT の行と対象の版を、同じ文字列のまま含めます。

### 3.5 用語

この節の語は、完成例と報告の要約でも使います。意味は次の表のとおりです。

| 語 | 意味 |
|---|---|
| 入口 | 外から要求を受け取る所。画面、API、ファイルの受け取り |
| 手口 | 攻撃のやり方の種類。A01〜A12 と、要求を送らない S01。番号ごとの中身は attack-baseline.md（新規。まだ無い）に置く |
| 再攻撃 | 直したあとに、同じ攻撃を全部送り直すこと |
| 未実施 | 当てはまるのに、送らなかった手口の数 |
| 前からある脆弱性 | このプロジェクトで最初に回した攻撃の結果に、すでにあった脆弱性 |
| 検出力 | 脆弱性を仕込んだサンプルで、仕込んだ数のうち見つけた数 |
| 常設の RoE | 攻撃してよい範囲と条件を決めた文書。プロジェクトごとに 1 回署名し、範囲が変わると切れる |
| ハッシュ値 | 中身から計算する短い値。中身が 1 字でも変われば、値も変わる |

## 4. 例

完成例は 2 本あり、配るコードを変えたかどうかで使い分けます。

| 完成例 | 場面 | 見どころ |
|---|---|---|
| `examples/completion-report-stage0.md` | 段階 0 の完了報告。欄を足す前の古い型で、新しく書く報告には欄を足す | 受け入れ条件 7 件の全行に確認コマンドと結果があり、未確認は理由つきで 2 件ある |
| `examples/completion-report-attack.md` | 配るコードを変えた実装の完了報告。題材は架空の通販の管理画面で、数値はすべて架空 | 先頭に攻撃の結果の節がある。他のプロジェクトの報告なので、検証の記録は `tmp/.verify/last-full.txt` を指す |
