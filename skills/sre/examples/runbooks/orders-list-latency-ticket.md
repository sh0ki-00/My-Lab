# Runbook: 注文一覧の遅さのチケット（OrdersListLatencyTicket）

> **3 行でわかる要約**
> 1. 注文一覧の API の遅い要求が少しずつ増え、遅さのエラーバジェットが 3 日で 10% 減る速さのときに、当番が開く手順書です。
> 2. 夜は起こさず、次の勤務の時間に直します。見本で起こせる原因は、読む件数が決めた量より多く、遅い要求が混じることです。
> 3. 確かめる命令で遅さの分かれ方と件数を見て、決めた量に戻してから、件数の伸びへの処置をバックエンドに起票してください。

| 項目 | 内容 |
|---|---|
| 通知 | `OrdersListLatencyTicket`（チケット。勤務の時間に直す） |
| 条件 | 3 日と 6 時間で、遅い要求がどちらも 1% 超え |
| SLO 定義書 | `../slo-order-list.md` |
| 対象 | 見本の API の写し。本番の命令は人が出し、AI は流さない |
| 数値 | 目標・閾値・時刻はすべて架空 |
| 訓練 | `../../scripts/runbook-drill.sh` が C7、表の外の 1 件、別の起動の 1 件を使い捨ての写しで起こし、この手順で直るかを確かめる |

## 用語

この節は、手順に出る略語と道具の名前をまとめます。2 回目からは説明を省きます。

| 用語 | 意味 |
|---|---|
| SLO | 利用者に約束する信頼性の目標。ここでは 30 日で 200 の要求の 99% が 50 ms 以内に返ること |
| SLI | 目標を測る数。ここでは 200 の要求のうち 50 ms 以内に返した割合 |
| エラーバジェット | 目標の外に出てよい遅い要求の量。30 日で 200 の要求の 1% |
| Runbook | 当番の手順書。通知 1 つに 1 本 |
| 外形の確かめ（probe） | 利用者と同じ道で一覧を呼ぶ確かめ。`sample-api.sh probe` |
| p50、p90 | 速い方から並べて 5 割目と 9 割目の時間 |

## 準備

この節は、命令が使う変数を決めます。どの命令の前にも、次の 2 行を流してください。

```sh
: "${API_DIR:=tmp/flow/stage5/api}" "${RUN:=tmp/flow/stage5/run}" "${PORT:=8080}" "${SRC:=samples/api}" "${SRE:=skills/sre/scripts}" "${KEYS:=$RUN/keys.txt}"
export API_DIR RUN PORT SRC SRE KEYS
```

| 変数 | 既定の値 | 意味 |
|---|---|---|
| API_DIR | tmp/flow/stage5/api | 見本の API の写し |
| RUN | tmp/flow/stage5/run | 要約のログ・pid・退避した file の置き場 |
| PORT | 8080 | 写しが 127.0.0.1 で待ち受けるポート |
| SRE | skills/sre/scripts | 当番の道具 |
| KEYS | $RUN/keys.txt | 作り物の鍵の file。無ければ道具が $RUN/keys.* を探す。pid の記録が無ければ、道具は PORT の待ち受けから写しの API を見つける。ほかの置き場の鍵は読まず、道具の鍵で入れなければ start が道具で立て直して作り直す |

## 症状

この節は、利用者に何が見えているかを書きます。一覧はたいてい速く出ますが、ときどき読み込みの印が見える程度に待たされます。速い要求と遅い要求が混じるのが、呼び出しの遅さとの違いです。

| 見えるもの | 利用者への影響 |
|---|---|
| p50 は 50 ms 前後で、p90 が 50 ms を超える | 操作の一部で、待たされる |
| 1 要求で読む行が、決めた量より多い | 件数が増えるほど、遅い要求の割合も増える |

このまま続くと 30 日で予算を使い切ります。件数が伸び続けるなら、呼び出しの条件に届きます。

## 確かめる命令

この節の命令は読むだけで、何も変えません。上から順に流し、出力をそのまま記録に貼ります。

```sh
bash "$SRE/sample-api.sh" probe --count 20
bash "$SRE/sample-api.sh" status
bash "$SRE/sample-api.sh" tally --last 200
```

| 命令 | 分かること |
|---|---|
| `sample-api.sh probe` | p50 と p90 の差。遅い要求が混じる形か |
| `sample-api.sh status` | 読む件数の設定（CONFIG）と決めた量の差 |
| `sample-api.sh tally` | 時間（DUR）の p50 と p99 |

## 原因の見分け方

この節は、確かめる命令の出力に出る印から、直す節を選ぶ表です。

| 原因 | 見えるもの | 印（確かめる命令の出力） | 直す節 |
|---|---|---|---|
| C7 読む件数が決めた量より多い | 遅い要求が混じる。件数の設定が決めた量と違う | `agreed=29 differ` | C7 |

件数が決めた量と同じなのに遅い要求が混じるときは、この表の外の原因です。記録を残し、バックエンドに問い合わせの数を測ってもらいます。

## 直す命令

この節は、原因ごとの直し方です。選んだ節の命令だけを流します。

### C7 読む件数が決めた量より多い

見本では、件数は起動の設定で決まります。決めた量で立て直します。本番では件数を減らせないので、索引か読む範囲の処置をバックエンドに起票します。

```sh
bash "$SRE/sample-api.sh" status | grep '^CONFIG'
bash "$SRE/sample-api.sh" stop
bash "$SRE/sample-api.sh" start --orders 29
```

## どれにも合わないとき

この節は、印が 1 つも出ないとき、または選んだ節のあとも直ったことの確かめが通らないときの手です。status の SEED が `SEED bad` か、FILE の行に `differ` が出たときもここです。正本の 4 つの file と決めた設定（件数 29）から写しを作り直し、立て直します。

```sh
bash "$SRE/sample-api.sh" rebuild
bash "$SRE/sample-api.sh" status
```

rebuild は、正本と違う file を消さずに `$RUN/broken/<時刻>/` へ移し、直す前の status と tally も残します。`REFUSE` か `FAILED` で終わったら、それ以上は触らずに 2 番手を呼びます。

そのあと、直ったかどうかに関わらず、SRE の 2 番手へ知らせます。知らせる文は次の型で、REBUILT の行に出た退避先を添えます。

> OrdersListLatencyTicket は Runbook の表の外でした。正本から写しを作り直し、直ったことの確かめは〈通った／通らない〉です。退避先は〈REBUILT の行のパス〉です。

## 直ったことの確かめ

この節の命令が終了コード 0 で終われば、遅さは閾値の内に戻っています。確かめは道具の probe と status だけで行い、出題役の命令や別の置き場の鍵は使いません。

```sh
bash "$SRE/sample-api.sh" probe --count 20 && bash "$SRE/sample-api.sh" status
```

| 確かめ | 合格 |
|---|---|
| probe | 20 回とも 200、50 ms 超えが 2 回以下、最後に GOOD |
| status | `agreed=29 same` |
| 通知 | 6 時間の遅い要求の割合が 1% を下回り、チケットが閉じる |

## 戻し方

この節は、直した操作が悪い方へ動いたときの戻し方です。

| 当番の操作 | 戻し方 |
|---|---|
| 決めた量で立て直した | 戻さない。件数が要る業務があるなら、バックエンドの処置が済んでから件数を上げる |
| 写しを正本から作り直した（表の外） | `$RUN/broken/<時刻>/` が調べる材料。戻すのは、作り手が直した file だけ |

## 記録と受け渡し

この節は、直したあとの仕事です。

| 渡す先 | 何を |
|---|---|
| バックエンド | 件数ごとの p50 と p90、1 要求で読む行の数 |
| 取りまとめ役 | 使ったエラーバジェット、処置の担当と期限 |
| SRE の 2 番手 | 表の外の手を使ったときの退避先と、表に足す印と訓練の注入の案 |
