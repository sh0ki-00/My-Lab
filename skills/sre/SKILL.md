# sre — 信頼性を数で約束し、写しで壊して確かめ、学びを仕組みに戻す

## いつ使うか

秘書の受付票で依頼の型が「信頼性」「通知」「障害」「リリースの可否」のとき。新しい API や画面に SLO を決めるとき、通知を足すか直すときに使う。Runbook の執筆と訓練、障害の記録、承認伺いに入れるリリースの可否の 1 行にも使う。API の契約と実装はバックエンド、基盤と復元はインフラ、検知の盲点と侵入テストはセキュリティが決めるので、このスキルでは決めない。

## 先に読むもの

- `.company/sre/CLAUDE.md`（ペルソナ）と `.company/DELIVERY.md`、`.company/rules/evidence-and-safety.md`。
- バックエンドの設計と実装計画（API 仕様、要約のログの項目、エラーの表、p99 の予算）。完成例は `skills/backend/examples/backend-plan-order-list.md`。
- インフラの構成設計書（測定点、通知の宛先、復元の手順）。完成例は `skills/infra/examples/infra-design-order-list.md`。無ければ仮置きにし、未確定に書く。
- `references/slo-and-error-budget.md`（測り点の選び方、目標と期間、承認、予算の扱い、可否の 1 行）。
- `references/burn-rate-alerting.md`（4 つの式、原典の推奨の表、多窓にする理由、要求の少ないサービス）。
- `references/runbooks-drills-incidents.md`（Runbook の 7 つの節と印、見本で起こせる原因 C1〜C7 と表の外、訓練の決まり、障害の記録、当番の上限）。
- `templates/`（`slo.md`、`runbook.md`、`incident.md`）、`examples/`（注文一覧の SLO 定義書、通知 4 つの Runbook、障害の記録）。見本の API は `samples/api/`。

## 判断の観点

1. 利用者に見える症状か。SLI は利用者に最も近い測り点で数え、原因の数（CPU やメモリ）では通知しない。基準は Google の SRE の本の 4 章と Workbook の 2 章。
2. エラーバジェットは残っているか。残量は測った値だけで語り、測れていなければ可否を返さない。使い切ったときの決まりは承認者が先に承認する。
3. 当番が Runbook どおりで止血に着くか。通知 1 つに Runbook 1 本、印の表で原因を 1 つに決め、書いた本人ではなく runbook-drill が写しで手順を通す。どの印にも合わない障害でも、正本から作り直す手と 2 番手への連絡で止血に着くか。
4. 戻せるか。戻しを訓練で実測し、Runbook に戻し方の節がある。直したあとも probe で利用者の道を確かめる。
5. 人ではなく仕組みを直しているか。障害の記録は人名で終えず、処置に担当・期限・完了条件を付ける。基準は Workbook の 5 章（多窓の通知）と、SRE の本の 15 章（非難しない振り返り）。

## 手順

1. 入力を読む。利用者の用事、API のエラーの表と要約のログの項目、インフラの測定点。終わりの印: 守る操作と利用者と時間帯を 1 文で言える。
2. SLI を決める。`templates/slo.md` を写し、測り点・有効な要求・良い要求を表にする。除く要求と除かない要求の理由を 1 文ずつ書く。
3. 目標と期間を決める。1 段上げた場合と下げた場合に利用者に何が起きるかを書き、予算を時間でも言う。架空か実測かを冒頭の表に書く。
4. エラーバジェットの扱いを書く。残りの段ごとの決まりを 4 行（50% より多い・0〜50%・使い切った・測れていない）で置く。1 件で 20% 以上を使ったときの記録の決まりも書く。
5. 通知を設計する。`scripts/burn-rate.sh --slo <目標> --period <期間>` の出力を通知の表に写し、SLI ごとに呼び出しとチケットを置く。終わりの印: `scripts/burn-rate.sh <定義書>` が食い違い 0 件。
6. Runbook を書く。通知 1 つに 1 本、`templates/runbook.md` を写す。症状・確かめる命令・原因の見分け方（印の表）・直す命令（C 番号の節）・どれにも合わないとき・直ったことの確かめ・戻し方。印は権限や状態だけでなく、正本との中身の照合（status の SEED と FILE）も使う。どれにも合わないときの節には、`scripts/sample-api.sh rebuild` で正本と決めた設定から写しを作り直す命令と、2 番手へ知らせる文の型を置く。命令は pid と鍵の置き場を決め打ちせず、`sample-api.sh pid` と道具の鍵の探索を使う。直す節は最後を `sample-api.sh start` で終え、道具の外で立てた API でも道具が立て直して鍵を作り直せる形にする。直ったことの確かめは道具の命令（`sample-api.sh probe` と `status`）だけにする。
7. 訓練する。`scripts/runbook-drill.sh <Runbook>...` が写しで原因ごとに障害を起こし、手順のコードだけで直るかを見る。Runbook ごとに表の外の 1 件と別の起動の 1 件も起こす。表の外は、どれにも合わないときの節で直るかを見る。別の起動は、出題役が道具の外の命令で立て、鍵を道具の読まない file に出した形で、原因の節と道具の probe で直るかを見る。出題役は自分の確かめの命令を渡さず、当番役は渡されても使わない。終わりの印: 全部 PASS。MEASURE の秒を定義書の訓練の表に写す。
8. 承認を取る。承認の表に承認者・立場・日付・判断を書く。承認は秘書が社長に伺い、AI は自分で埋めない。終わりの印: `scripts/slo-doc-check.sh <定義書>` が PASS。
9. リリースの可否を返す。予算の残量を測った日と値を書き、`references/slo-and-error-budget.md` の表から 1 行を選ぶ。残量が未実測なら「返さない」と書く。
10. 障害や当番役の訓練のあとは、`templates/incident.md` で記録を書く。節は影響の数・時系列・検知と止血・仕組みの原因・処置の 3 点・学びの 6 つ。Runbook の外の手を使ったら、その原因の印の行と訓練の注入を足す。
11. 月に 1 回、月次の信頼性レビューを書く。見るのは当番の呼び出しの数・Runbook の無い通知・予算の使い方・処置の期限切れの 4 つ。

## 出力と受け渡し

| 成果物 | 置き場 | 渡す先 |
|---|---|---|
| SLO 定義書 | `tmp/flow/<件名>/slo.md` | 秘書（承認の行と、予算の残量と可否の 1 行を伺いに写す） |
| Runbook（通知 1 つに 1 本） | `tmp/flow/<件名>/runbooks/` | 当番、セキュリティ（検知の通知と Runbook の置き場） |
| 訓練の記録 | 定義書の訓練の表、`tmp/flow/<件名>/drills.md` | 秘書（MEASURE の秒だけ） |
| 障害の記録 | `tmp/flow/<件名>/incidents/` | 秘書（影響・予算・処置）、処置の担当の役割 |
| 月次の信頼性レビュー | `docs/review-<年月>.md` | 秘書（要約） |
| SLI の測定点と通知の条件 | 定義書の SLI と通知の節 | バックエンド、インフラ |
| 応答時間の SLO と、超えたときの画面の振る舞い | 定義書の目標の節 | フロントエンド |

秘書には、要約 10 行以内・未解決の対立・承認が要る判断の 3 つを `skills/secretary/templates/reply-from-role.md` の型で返す。承認が要るのは、SLO の目標の値、予算を使い切ったときの止める決まりと例外、当番の上限である。

## 禁止

- 測っていない数値を残量・実測・達成率として書く。残量が不明のまま可否を言う。架空の数値を架空と書かずに置く。
- 承認者の無い SLO を出す。AI が承認の行を自分で埋める。
- API のログや CPU など、利用者から遠い数だけで SLI を決める。原因の数で当番を起こす。
- 通知を増やして Runbook を増やさない。2 つの通知で 1 本の Runbook を使い回す。当番の上限を超えたまま放置する。
- 本番で障害を注入する。本番の切り替え・切り戻し・注入の命令を AI が流す。samples/ の正本に障害を起こす。訓練の注入を 127.0.0.1 の外へ向ける。
- 本物の鍵をファイルや出力に書く。訓練の鍵は起動のたびに作る作り物にし、止めたら消す。鍵の置き場を `$KEYS` のほかに増やす。
- 原因を人名で終える。担当・期限・完了条件の無い処置。
- 他の役割の判断を代行する。承認のない commit・push・Issue と PR の作成。

## 提出前の確認

1. `scripts/slo-doc-check.sh <定義書>` と `scripts/burn-rate.sh <定義書>` が PASS。
2. `scripts/runbook-drill.sh <定義書から結ばれた Runbook の全部>` が PASS。MEASURE の秒を定義書に写した。
3. 定義書・Runbook・障害の記録が `tools/check-file.sh` と `tools/check-refs.sh` を通る。
4. `bash skills/sre/evals/run.sh` が PASS（原典の表との照合を含む）。
5. 読み手テストは秘書が `editor` に頼む（SRE からは呼べない）。当番役の確かめは runbook-drill の結果で示す。
6. 秘書に返す 3 つ（要約・未解決の対立・承認が要る判断）が `skills/secretary/scripts/reply-check.sh` を通る。
