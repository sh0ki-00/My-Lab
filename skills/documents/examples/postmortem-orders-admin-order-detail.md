## 1. 要約

2026-11-04 の 10:15 から 23 分間、管理画面の注文詳細が開けなかった。店の担当者 4 人と管理者 1 人の注文の確認が止まった。直接の原因は、注文 API の新しい版が読む秘密情報が本番のタスク定義（コンテナの起動設定）に無かったことである。健康確認の応答は正常だったため自動の切り戻しは働かず、当番の依頼を受けたインフラ役の手による切り戻しで復旧した。

## 3. 背景と用語

- 注文 API は ECS Fargate（コンテナを動かす AWS の仕組み）のサービス orders-api（平常 2 台）で動き、版の切り替えはタスク定義の更新で行う。
- 健康確認（/healthz）は ALB と ECS が使う応答で、設定の読み込みや秘密情報の有無は見ていなかった。
- デプロイ・サーキットブレーカーは、起動に失敗し続けたときだけ前の版に戻す ECS の仕組みである。
- 秘密情報は AWS の保管庫 Secrets Manager に置き、タスク定義の環境変数として注文 API に渡す。

## 4. 経緯（障害の前にあったこと）

- 10 月末に、注文の発送通知を外部の配送会社の API に送る機能が注文 API に入った。同じ版で注文詳細の画面に配送状況の欄が付き、詳細の要求ごとに配送会社の API を呼ぶ。この機能は新しい秘密情報（配送会社の API 鍵）を、起動時ではなく要求時に読む。
- 動作確認は検証 stg で通っていた。stg では秘密情報が手で足されていたので通り、本番の構成コードにはその定義が無かった。
- リリース作業手順書の事前確認は、イメージの存在と健全性と台数を見ていた。新しい版が必要とする設定の差分は見ていなかった。

## 8. 根本原因と引き金

| 区分 | 内容 |
|---|---|
| 引き金 | 注文 API の新しい版（配送通知の機能を含む）を本番に配備したこと |
| 根本原因 | 注文 API が、必要な設定の有無を起動時に確かめず、要求を受けたときに初めて失敗する作りだったこと。健康確認も設定を見ないため、自動の切り戻しが働かなかった |
| 寄与要因 | (1) 検証 stg の秘密情報を手で足し、構成コードとの差分が残っていた。(2) リリース手順の事前確認に、新しい版が必要とする設定の差分を見る行が無かった。(3) 当番に update-service の権限が無く、切り戻しに人を 1 人挟んだ |

## 11. やらないと決めた対策

| 対策 | やらない理由 |
|---|---|
| 本番で 1 台だけ新版にして様子を見る（カナリア配備） | 平常 2 台の構成では費用と手間に見合わない。台数が 4 台を超えたら月次の信頼性レビューで再検討する |
