# orders-admin 注文一覧の絞り込み 要件定義書

| 項目 | 内容 |
|---|---|
| 対象 | orders-admin（注文管理画面と注文 API）の注文一覧に、注文番号・期間・状態の絞り込みを足す |
| 決める人 | 社長 |
| 作成者 / 確認者 | 秘書 / バックエンド役・フロントエンド役 |
| 状態 | 下書き（見本アプリの文書で、数値は架空。承認の伺いの前） |
| 準拠 | 非機能要件は非機能要求グレード 2018（IPA、情報処理推進機構）の大項目 A〜F に合わせた。変えた項目は無い |
| 様式 | 見本アプリに既存の要件定義書が無いので、`skills/documents/templates/requirements.md` の雛形を使った |
| 版 | 1.0（2026-11-11） |

## 1. 目的と背景

店の担当者は、問い合わせを受けた注文を一覧から探すのに中央値で 170 秒かかる。値は 2026-11-05 に 20 件を観察した結果で、一覧は新しい順に 50 件ずつ送るだけで条件で絞れない。探す時間が問い合わせの回答を遅らせている。そこで注文番号・期間・状態で絞れるようにし、1 件を 30 秒以内に開けるようにする。

## 2. ゴールと管理指標

| 指標 | 現在の値 | 目標の値 | 測り方 | 測る時期 |
|---|---|---|---|---|
| 注文 1 件を開くまでの時間（中央値） | 170 秒（2026-11-05、20 件の観察） | 30 秒以内 | 管理画面のログで、一覧を開いてから詳細を開くまでの時間を取る | リリース後 4 週間の全件 |
| 問い合わせへの回答までの時間（平均） | 25 分（10 月のチャットの記録 41 件） | 20 分以内（探す時間の短縮 140 秒と、探し直しが無くなる分を見込む） | チャットの受信から返信までの時間 | リリース後 4 週間 |

## 3. 利害関係者と決める人

| 役割 | 誰 | 決めること |
|---|---|---|
| 決める人 | 社長 | 要件の採否、未決事項、完了の判断 |
| 利用者 | 店の担当者 4 人、管理者 1 人 | 受け入れの実演で、使えるかを言う |
| 作る人 | バックエンド役（注文 API）、フロントエンド役（管理画面） | 作り方。要件は変えない |
| 守る人 | セキュリティ役、SRE 役 | 入力の検査の観点、監視と性能の測り方 |

## 4. 用語定義

| 用語 | 意味 |
|---|---|
| 注文番号 | 注文 1 件に付く 10 桁の数字。重複しない |
| 注文状態 | 受付・発送済み・取消の 3 値。「返品」を足すかは OI-002 |
| 期間 | 注文日時の開始と終了。日付で指定し、終了の日の 23:59:59 まで含む |
| 絞り込み | 一覧に条件を掛け、合う注文だけを表示すること |
| カーソル | 一覧の続きを取るための印。注文日時と注文番号の組 |
| 優先度 | Must（必須）・Should（重要）・Could（あれば良い）・Won't（今回はやらない）の 4 段。Should と Could が通らなくても受け入れは止めない |
| 検証方法 | 試験（自動か手の試験）・実演（利用者の前で動かす）・検査（文書や設定を見る）・解析（計算や計測）の 4 つ |
| stg | 本番と同じ構成コードで作る検証環境 |
| p95 | 100 回のうち 95 回が収まる値。平均より遅い側を表す |
| 400 | 入力の誤りを示す応答の番号。文を添えて利用者に見せる |

## 5. 範囲と対象外

| 区分 | 内容 | 理由 |
|---|---|---|
| 範囲（業務） | 店の担当者と管理者が、注文を探して開く業務 | - |
| 範囲（システム化） | 管理画面の注文一覧に条件欄を足す。注文 API の一覧取得に条件を足す。注文の表に索引を足す | - |
| 対象外 | 商品名の部分一致による検索 | 全文検索の仕組みが要り、今回の期間に収まらない。14 章の保留へ |
| 対象外 | 顧客名と電話番号による検索 | 個人情報を検索条件とログに通す決まりを先に決める |
| 対象外 | 絞った結果の CSV 出力 | 別の依頼として受付票を書く |

## 6. 前提と制約

| 区分 | ID | 内容 | 由来 |
|---|---|---|---|
| 前提 | AS-001 | 注文はいま 12 万件（2026-11-05）で、1 日 400 件以内で増え、3 年で 36 万件を超えない | 2026-11-05 の件数と、10 月の実績 1 日 320 件からの見込み |
| 前提 | AS-002 | 一覧の続きは、いまのカーソル方式のまま取る | 既存の注文 API |
| 前提 | AS-003 | リリースは 2026-12-04（金）のリリース窓に乗せ、実装は 2026-11-27 までに終える | 社長との打ち合わせ（2026-11-10） |
| 制約 | CN-001 | 管理画面には事務所の回線からだけ入れる。WAF（通信を通すか止めるかを決める仕組み）の既定は変えない | 組織（セキュリティの決まり） |
| 制約 | CN-002 | 注文の表の構造（列と型）は変えない。索引の追加だけ許す | 連携先（会計システムが同じ表を読む） |
| 制約 | CN-003 | 顧客の氏名と電話番号を検索条件にも、ログにも残さない | 法令（個人情報保護法） |

## 7. 業務要件

| ID | 業務 | 現行（As-Is） | 新業務（To-Be） | 業務量と時期 | 優先度 |
|---|---|---|---|---|---|
| BR-001 | 問い合わせを受けた注文を開く | 一覧を新しい順に送り、目で探す | 注文番号か、期間と状態で絞って開く | 1 日 30〜60 回。10:00〜19:00 | Must |
| BR-002 | 当日の未発送の注文を一覧で見る | 全件から未発送を目で拾う | 状態「受付」と期間「当日」で絞る | 1 日 2 回。10:00 と 16:00 | Should |

## 8. 機能要件

要件文は「条件のとき、システムは応答する」の形で、1 文 1 要件にした。異常時は正常時と同じ重さで書き、受け入れ基準には異常時の結果も入れる。

| ID | 分類 | 要件文 | 異常時 | 根拠（出典） | 優先度 | 受け入れ基準 | 検証方法 | 関連 |
|---|---|---|---|---|---|---|---|---|
| FR-001 | 画面 | 注文一覧を開いたとき、管理画面は注文番号・期間・状態の 3 つの条件欄を表示する | 条件欄の描画に失敗したとき、一覧は条件なしで表示する | BR-001 | Must | 前提: 一覧を開く。操作: 何もしない。結果: 3 つの条件欄と、条件なしの一覧が出る | 実演 | BR-001 |
| FR-002 | 振る舞い | 注文番号が入力されたとき、注文 API は番号が一致する注文だけを返す | 10 桁の数字でない値のとき、400（入力の誤りを示す応答の番号）と「注文番号は 10 桁の数字」の文を返す | BR-001 | Must | 存在する番号で 1 件、存在しない番号で 0 件、9 桁の番号で 400 | 試験 | BR-001 |
| FR-003 | 振る舞い | 期間の開始と終了が入力されたとき、注文 API は注文日時がその範囲にある注文を返す | 開始が終了より後か、範囲が 93 日（TBR。確認中の仮の値、OI-001）を超えるとき、400 と「期間は開始が終了以前で、93 日以内」の文を返す | BR-001、BR-002 | Must | 11-01〜11-07 で、7 日分の件数と一致する。開始と終了が逆、94 日の期間で 400 | 試験 | BR-001、BR-002 |
| FR-004 | 振る舞い | 状態が選ばれたとき、注文 API は選ばれた状態の注文だけを返す | 定義に無い状態の値のとき、400 と「状態は受付・発送済み・取消のどれか」の文を返す | BR-002 | Must | 「受付」で絞った結果に他の状態が 0 件。定義に無い値で 400 | 試験 | BR-002 |
| FR-005 | 振る舞い | 2 つ以上の条件が入力されたとき、注文 API は全部の条件を満たす注文だけを返す | 片方の条件が不正なとき、その条件の 400 を返す | BR-001 | Must | 番号と状態の両方を指定し、両方を満たす 1 件だけが返る。片方が不正なら、その条件の 400 | 試験 | BR-001 |
| FR-006 | 画面 | 絞り込みの結果が 0 件のとき、管理画面は「条件に合う注文はありません」と入力した条件を表示する | - | BR-001 | Should | 存在しない番号で、文と入力した番号が表示される | 実演 | BR-001 |
| FR-007 | 画面 | 条件を変えて再表示したとき、管理画面は再読み込みの後も同じ条件と同じ結果を出す | 保存していた条件が不正なとき、FR-002〜FR-004 の 400 の文を出す | 店の担当者の聞き取り（2026-11-05） | Could | 再読み込みの後に、同じ 3 条件と同じ件数が出る | 実演 | BR-001 |
| FR-008 | 振る舞い | 商品名が入力されたとき、注文 API は商品名が部分一致する注文を返す | - | 店の担当者の聞き取り（2026-11-05） | Won't | - | - | 14 章の保留 |

## 9. 非機能要件

| ID | 項目 | 要求値 | 根拠 | 優先度 | 検証方法 |
|---|---|---|---|---|---|
| NFR-A-001 | A 可用性: 稼働率 | 注文 API の月の稼働率 99.9% を下げない | 運用設計書 6 章の SLO（利用者に約束した数値） | Must | 解析（月次の SLO 報告） |
| NFR-B-001 | B 性能・拡張性: 一覧の応答時間 | 条件付きの一覧取得が p95 で 1.0 秒以内。注文 12 万件、同時 5 利用者 | いまの一覧は p95 で 0.8 秒（2026-11-05 の計測）。条件を足しても増加を 0.2 秒以内に収める | Must | 試験（stg に 12 万件を入れて測る） |
| NFR-B-002 | B 性能・拡張性: 件数の増え方 | 注文 36 万件でも NFR-B-001 を満たす | AS-001 | Should | 試験（stg に 36 万件を入れて測る） |
| NFR-C-001 | C 運用・保守性: 監視 | 注文 API の 5xx（サーバー側の失敗を示す応答の番号）を既存のアラームで数える。新しいアラームは足さない | 運用設計書 6 章 | Must | 検査（アラームの一覧） |
| NFR-D-001 | D 移行性: データ移行 | 無し。索引を 2 つ足すだけで、表の構造は変えない | CN-002 | Must | 検査（移行の文の一覧） |
| NFR-E-001 | E セキュリティ: 検索条件の記録 | ログに残す条件は注文番号・期間・状態だけ。顧客の情報は条件に無い | CN-003 | Must | 検査（ログの項目の一覧） |
| NFR-E-002 | E セキュリティ: 入力の検査 | 3 つの条件を注文 API 側で形式検査し、不正な値は 400 で返す | セキュリティ役の観点 | Must | 試験（不正な値 6 種: 9 桁の番号、数字でない番号、開始が終了より後、94 日の期間、定義に無い状態、形式の違う日付） |
| NFR-F-001 | F システム環境: 利用する閲覧ソフト | FR-001 と FR-006 の受け入れ基準が、事務所の端末の Chrome と Edge の最新版で通る | 事務所の端末の一覧 | Should | 実演 |

## 10. 移行・運用・教育・テストの要件

| 区分 | ID | 内容 | 優先度 |
|---|---|---|---|
| 移行 | TR-001 | 注文の表に索引を 2 つ足す作業を、リリース窓（平日 10:00〜16:00）の中で行う。作成の時間は stg の 12 万件で測り、1 分を超えるなら夜間に変える | Must |
| 運用 | TR-002 | 運用項目は増やさない。リリースは注文 API リリース作業手順書に沿って進める | Must |
| 教育 | TR-003 | 店の担当者 4 人に 10 分の説明をする。資料は条件欄の画面の写し 1 枚 | Should |
| テスト | TR-004 | 8 章と 9 章の検証方法を stg で全部通し、結果を Issue（GitHub の課題票）に貼る | Must |

## 11. 受け入れ基準と検証方法

受け入れは、8 章と 9 章の全行の検証方法を通し、2 章の指標を測って判断する。測り方を決められない要件は、受け入れ基準から外して設計方針に移す。

| 確かめること | 合格の条件 | 確かめ方 | 確かめる人 |
|---|---|---|---|
| 絞り込みの正しさ | FR-002〜FR-005 と NFR-E-002 の試験が全部通る | stg で試験を回し、結果を Issue に貼る | バックエンド役 |
| 応答時間 | NFR-B-001 を満たす | stg に 12 万件を入れ、同時 5 利用者で p95 を測る | SRE 役 |
| 画面 | FR-001、FR-006、FR-007 の実演が通る | 店の担当者 2 人が stg で実演し、秘書が立ち会う | 秘書 |
| 指標 | 2 章の 2 つの指標が目標の値に届く | リリース後 4 週間の管理画面のログと、チャットの記録を集計する | SRE 役 |
