# My-Lab 検証と守り 運用設計書

| 項目 | 内容 |
|---|---|
| 対象システム | My-Lab（会社の形と役割スキルのリポジトリ） |
| 対象環境 | 社長の Mac の作業場と、GitHub の sh0ki-00/My-Lab |
| 作成 / 承認 | 秘書 / 社長 |
| 様式 | My-Lab に既存の運用設計書が無いので、`templates/ops-design.md` の雛形を使った |
| 数値の出どころ | `tools/verify-all.sh`、`hooks/`、`docs/verify/` の記録。測っていない値は「未測定」と書く |
| 版 | 1.1（2026-11-11。資料の型から現場の文書の型に直した） |

## 1. 運用の基本方針

- 検証を回さずに「完了」と書かない。FAIL のあいだは完了と書かず、直すのは自分が変えたファイルだけにする。
- 外に出る操作は、そのたびに社長の承認の言葉を得る。commit、push、Issue と PR の作成がこれに当たる。守りの hooks（コマンドの直前と編集の直後に走る検査）が機械で止める。
- 守りの設定と常時ルールは社長だけが書く。AI は差分を示して止まる。
- 指示されていないファイルは変えない。範囲外の FAIL は報告に書いて終える。

## 2. 対象システム

My-Lab は、会社の決まりと役割のスキルと守りと検証の道具を置くリポジトリである。置き場は `.company/`・`skills/`・`hooks/`・`tools/` の 4 つに分かれる。作業は Claude Code と Cursor から行い、成果物は `tmp/flow/` に、検証の記録は `docs/verify/` に残す。他のプロジェクトへは `deploy.sh` で一式を `tmp/` に写す。

| 部品 | 名前 | 役目 |
|---|---|---|
| 守り | `hooks/guard-core.sh`、`hooks/claude-postedit.sh`、`hooks/claude-stop.sh` | 命令の判定（許可・確認・拒否）、編集の直後の検査、作業の終わりの検証 |
| 守りの設定 | 守りの強さの設定ファイル（管理者 root 所有。置き場は `AGENTS.md` の守りの表） | 社長が `sudo` で書く。AI は読むだけ |
| 検証 | `tools/verify-all.sh`、`tools/check-file.sh`、`tools/lib/*.py` | 全体の検証（11 種類）と、1 ファイルの検査 |
| 記録 | `docs/verify/<日付>.md`、`tmp/.verify/` | `--full` の記録と、`--fast` の記録と詳細のログ |
| 配布 | `deploy.sh`、`tools/project-verify.sh` | 他のプロジェクトの `tmp/` へ写す。写した先の検証 |
| 置き場 | GitHub の sh0ki-00/My-Lab | 正本。main へは PR で入れる |

## 3. 運用体制

### 3-1. 役割分担

| 役割 | 担当 | 受け持ち |
|---|---|---|
| 依頼と承認 | 社長 | 依頼を出し、承認の言葉を残し、守りの設定と常時ルールを書く |
| 受付と門 | 秘書 | 受付票、承認伺い、完了報告。検証の結果を読み、FAIL を直す |
| 作る | 役割（サブエージェント。会話の履歴を持たない別の AI） | 承認の範囲で成果物を書き、直したファイルを検査する |
| 機械の守り | hooks | 編集の直後の検査、作業の終わりの検証、外に出る操作の確認 |

### 3-2. 連絡先と時間

| 連絡先 | 経路 | 受ける時間 |
|---|---|---|
| 社長 | Claude Code か Cursor のチャット | 社長が開いているとき。決めた時間は無い |
| 秘書 | 同じチャット | 社長の依頼のたび |

### 3-3. 連絡と上申の順

1. 検証の FAIL は、自分が直したファイルなら直して回し直す。知らせるのは 3 回直しても通らないときだけで、FAIL の行と試した直し方を社長に伝える。
2. 触っていないファイルの FAIL は直さず、完了報告の「未確認」にファイルと FAIL の行を書く。
3. 守りが commit や push を止めたら、止められた命令をそのまま社長に見せて承認を待つ。合図の語を AI が付けることはしない。

## 4. 運用項目一覧

| No | 分類 | 運用項目 | 作業内容 | 時期・きっかけ | 担当 | 手順書 | 備考 |
|---|---|---|---|---|---|---|---|
| 1 | 基盤運用 | 直したファイルの検査 | `tools/check-file.sh` で、そのファイルの文体・型・構文を見る | 自動（ファイルを直した直後） | hooks、秘書か役割 | `skills/verify/references/checks.md` | FAIL は直してから次へ進む |
| 2 | 基盤運用 | 作業の終わりの検証 | `tools/verify-all.sh --fast` を回す | 自動（作業を終えるとき） | hooks、秘書か役割 | `skills/verify/references/checks.md` | 記録は `tmp/.verify/last-fast.txt` |
| 3 | 基盤運用 | commit 前の検証と記録 | `tools/verify-all.sh --full` を回し、記録を残す | 依頼（commit の承認を伺う前） | 秘書 | `procedure-verify-before-commit.md` | 記録は `docs/verify/<日付>.md` |
| 4 | 基盤運用 | 守りの自己試験 | `hooks/selftest.sh` で判定の規則を試す | 自動（全体の検証の中） | hooks | `skills/verify/references/checks.md` | 2 つの言語設定で回る |
| 5 | 運用管理 | 守りの設定の切り替え | 守りの強さの設定ファイルを書き換える | 社長の判断 | 社長 | 未整備 | 管理者（root）所有のファイルで、社長が `sudo` で書く |
| 6 | 運用管理 | 写した先への配布 | `deploy.sh` で一式を他のプロジェクトの `tmp/` に写す | 依頼（決まりや検査を変えて main に入れたあと） | 社長 | `deploy.sh` の冒頭の使い方 | 写した先の検査は `tools/project-verify.sh` |
| 7 | 運用管理 | 検査の道具の更新 | shellcheck、gitleaks、trivy、semgrep、jq、node を入れ直す | 通知（検査が `[道具が無い]` を出したとき） | 社長 | 未整備 | 無いときは FAIL と同じに扱い、社長に伝える |
| 8 | 業務運用 | 依頼の受付から完了報告 | 受付票、承認伺い、承認記録、完了報告を書く | 依頼のたび | 秘書 | `skills/secretary/SKILL.md` | 成果物は `tmp/flow/<件名>/` |

## 5. 運用カレンダー

| 周期 | 時期 | 作業 | 担当 |
|---|---|---|---|
| 編集のたび | ファイルを直した直後 | No 1 | hooks |
| 作業のたび | 作業を終えるとき | No 2 | hooks |
| commit のたび | 承認を伺う前 | No 3、No 4 | 秘書 |
| main が進むたび | PR の merge のあと | No 6 | 社長 |
| 不定期 | 社長の判断、検査の通知 | No 5、No 7 | 社長 |

## 6. 監視

| 監視項目 | 条件 | 通知先 | 一次対応 |
|---|---|---|---|
| 直したファイルの検査 | `check-file.sh` が FAIL | チャット（hooks が返す） | 自分のファイルなら直す。範囲外なら完了報告の「未確認」へ |
| 作業の終わりの検証 | `verify-all.sh --fast` が FAIL | チャット（hooks が返す） | 同上。FAIL のあいだは「完了」と書かない |
| 外に出る操作 | `git commit`、`git push`、`gh pr create`、`gh issue create` | 確認の表示（ask） | 社長が承認するか止める |
| 守りの設定への書き込み | 守りの設定の置き場への書き込みと削除 | 拒否の表示（deny） | 社長が `sudo` で書く |
| 道具の欠け | `FAIL … [道具が無い]` | 検証の出力 | FAIL と同じに扱い、社長に道具の名前を伝える |

## 7. バックアップとリストア

| 対象 | 方式 | 周期 | 保持 | 復元の手順書 | 目標復旧時点（RPO）/ 目標復旧時間（RTO） |
|---|---|---|---|---|---|
| リポジトリ | git の履歴と GitHub の正本 | commit と push のたび | 無期限（履歴） | 未整備（`git clone` で戻す） | 直前の push / 未測定 |
| 検証の記録 | `docs/verify/` を git で管理 | `--full` のたび | 無期限（履歴） | 同上 | 同上 |
| `tmp/` の成果物 | 無い（git の無視の対象） | なし | 次に上書きするまで | なし | 戻せない。必要な成果物は commit の対象へ写す |

## 8. ログ管理

| ログ | 置き場 | 保持 | 見る人 |
|---|---|---|---|
| 全体の検証（`--full`）の記録 | `docs/verify/<日付>.md` | 無期限（git） | 秘書（完了報告のたび）、社長 |
| 検証の詳細 | `tmp/.verify/verify-full.log`、`gitleaks.err`、`trivy.out`、`semgrep.out` | 次に回すまで（上書き） | 秘書（FAIL の原因を読むとき） |
| `--fast` の記録 | `tmp/.verify/last-fast.txt` | 次に回すまで（上書き） | 秘書か役割 |
| 受付票、承認伺い、承認記録、完了報告 | `tmp/flow/<件名>/` | 未決（git の対象外） | 秘書、社長 |

## 9. 障害時の処置

| レベル | 状態 | 最初の処置 | 知らせる相手 |
|---|---|---|---|
| 1 | 守りが効かない（`hooks/selftest.sh` が FAIL、または止まるべき命令が通った） | 外に出る操作を止め、`hooks/selftest.sh` の FAIL の行を控える | 社長（すぐ） |
| 2 | 全体の検証が通らない（自分の変更以外の FAIL） | 直さずに FAIL の行を控え、完了報告の「未確認」に書く | 社長（完了報告で） |
| 3 | 道具が無い、文字の設定が無い | FAIL と同じに扱い、作業を止める | 社長（道具の名前を添えて） |

障害の記録と振り返りは、`tmp/flow/<件名>/` の完了報告と、必要ならポストモーテムに残す。

## 10. 変更管理とリリース

| 段階 | すること | 誰 |
|---|---|---|
| 依頼 | 社長の 1 行の依頼を受付票にする | 秘書 |
| 承認（関所 1） | 承認伺いを 1 枚にし、社長の言葉を承認記録に残す | 秘書、社長 |
| 作る | 作業ブランチで、承認の範囲のファイルだけを直す | 役割、秘書 |
| 検証 | `tools/verify-all.sh --full` を回し、完了報告を書く | 秘書 |
| 承認（関所 2） | commit と push の承認の言葉を得る | 社長 |
| 本番反映 | PR を作り、main に merge する。写した先へは `deploy.sh` | 社長 |

## 11. アカウントと権限

| 権限 | 持つ人 | 付与と回収 |
|---|---|---|
| GitHub の sh0ki-00（push、PR の merge） | 社長 | 社長の個人のアカウントだけを使う。AI は鍵を持たない |
| 守りの設定（root 所有）への書き込み | 社長 | `sudo` で書く。AI は拒否される |
| 作業場のファイルの読み書き | 秘書、役割 | 承認の範囲で。`hooks/` と `.claude/settings.json` は書かない |
