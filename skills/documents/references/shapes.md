# 文書の 6 つの形と、相手の形の探し方

> **3 行でわかる要約**
> 1. 6 種類の文書の形と、写した先の既存の文書に合わせる手順をまとめた文書である。
> 2. 6 種類は手順書・運用設計書・調査報告書・ポストモーテム・要件定義書・仕様書で、2 つの型に分かれる。
> 3. 形が守れているかは `skills/documents/scripts/shape-check.sh` が見る。種類ごとの必須の節と、表の列と語の決まりで落とす。

## 1. 相手の形を正本にする

写した先には、その会社の手順書や要件定義書が既にあることが多い。読み手はその形に慣れているので、私たちの型を持ち込むと「手順書じゃない」と言われる。だから最初に相手の形を探し、あればそれを正本にする。

| 手順 | すること | 終わりの印 |
|---|---|---|
| 1 | 作業中のプロジェクトの docs、mkdocs、README の下を ls で見る。別のプロジェクトは見ない | 同じ種類の文書の候補が並ぶ |
| 2 | 候補を 1 本 cat で開き、節の名前、文体（常体かですます調か）、表とコマンドの置き方を書き留める | 3 点が書き留まる |
| 3 | 自分の文書の節構成と文体を、書き留めた形に合わせる。足りない節は雛形から補ってよいが、相手の節は消さない | 相手の文書と並べて違和感が無い |
| 4 | 文書情報の表の「様式」か要約の 3 行目に、「既存の〇〇に合わせた」か「無いので雛形を使った」と書く | 読み手が出どころを知れる |

## 2. 資料の型と現場の文書の型

6 種類は 2 つの型に分かれる。判断する人が読む文書は要約から始め、現場で使う文書は文書情報の表から始める。どちらの型かで、冒頭と節の 1 文目の決まりが変わる。

| 型 | 文書 | 冒頭 | 節の形 | 読み手の説明と用語 |
|---|---|---|---|---|
| 資料の型 | 調査報告書、仕様書 | 3 行の要約。続けて文書情報の表 | 節の 1 文目で要点を言い、図か表で支える | 用語の節を置く。英語は初出で括弧説明 |
| 現場の文書の型 | 手順書、運用設計書、要件定義書、ポストモーテム | 表題の直下に文書情報の表。要約は書かない | 表と番号付きの行が芯。節は表から始めてよい | 読み手の説明の節は置かない。用語は要件定義書の用語定義と、ポストモーテムの背景と用語の節にだけ置く |

文体は相手に合わせる。雛形は、資料の型をですます調、現場の文書の型を常体で書いている。

## 3. 手順書の形

手順書の読み手は、操作の行を見ながら手を動かす。理由を読まないと次に進めない書き方は、作業の途中で読み手を止める。だから操作の行には 4 つだけを置き、理由と背景は「注意事項」の節に集める。

| 置くもの | 書き方 |
|---|---|
| 番号 | 1 行に 1 操作。段階が長ければ小見出しで区切る |
| 操作 | 動詞で終える 1 文。「〜する」「〜を開く」 |
| コマンドか画面 | 操作の直下のコードブロック。画面なら、どのメニューのどのボタンか |
| 期待結果 | 続きの行に「期待結果: 〜になる」。違ったときに進む節を添える |

良い例と悪い例を並べる。悪い例は、操作の前に理由が 2 段落あり、コマンドは付録にある。

```text
悪い例
### 3. 検査元の IP を通す
許可 IP の正は allow_ip_addresses.yml です。このファイルは 5 つの環境で共用です。
いまの WAF では優先度 6 が国外の遮断で、優先度 7 が許可 IP 以外の遮断です。だから…（理由が続く）
1. yml の末尾に、付録の 2 行を足す。

良い例
### 3. 検査元の IP を通す
1. allow_ip_addresses.yml の末尾に次の 2 行を足す。
     - 203.0.113.0/29
     - 198.51.100.7/32
   - 期待結果: 差分が 2 行の追加だけになる。
2. 作業する環境だけで plan を実行し、差分が WAF と IP セットだけであることを確かめる。
   - 期待結果: 他の環境の資源が差分に出ない。出たら 6-1 の判断へ。
（理由は「注意事項」に。優先度 6 と 7 の遮断が先に掛かるため、優先度 0 の許可が要る）
```

雛形の節は 7 つで、検査が必須にするのは目的・前提・手順・確認・切り戻し・記録の 6 語である。事前確認は確認項目・確認方法・期待結果の表にし、作業記録はそのまま埋める枠にする。相手の手順書に同じ役目の節があれば、名前は相手に合わせる。

## 4. 運用設計書の形

運用設計書の芯は運用項目一覧である。誰が、何をきっかけに、どの手順書で、どのくらいの頻度で手を動かすかが 1 行で分かる。設計書の型（背景・目標・代替案・流出経路図）は使わない。

| 節 | 中身 |
|---|---|
| 運用の基本方針 | 何を守るための運用か。SLO（利用者に約束した数値）があれば数値で |
| 対象システム | 構成と環境、関わる人 |
| 運用体制 | 役割分担、連絡先と時間、連絡と上申の順 |
| 運用項目一覧 | 1 行 1 項目。作業概要、きっかけ（依頼・通知・定期）、担当、頻度、手順書への参照 |
| 運用カレンダー、監視、バックアップとリストア、ログ管理 | 定期の作業の月と日、見る値と通知、取る物と戻す手順、残す期間 |
| 障害時の処置、変更管理とリリース | 検知から復旧までの流れと連絡、変更の承認とリリース窓 |
| アカウントと権限、セキュリティ更新、定期報告 | 誰が何に入れるか、更新の周期、報告の相手と頻度 |
| 関連文書一覧、未決事項、改訂履歴 | 手順書と設計書への参照、決まっていない頻度や担当、版 |

頻度と日数は測った値か決めた値だけを書く。どちらも無ければ未決事項に置き、決める人を添える。検査が必須にするのは方針・体制・運用項目・監視・バックアップ・障害・変更の 7 語である。

## 5. 調査報告書の形

調査報告書は、判断する人が結論と根拠だけを知るために読む。調べた順ではなく、問い・範囲・方法・比較・未確認・結論・出典の順に並べる。比較表のセルには事実と根拠だけを書き、解釈は考察と結論に分ける。

| 節 | 中身 |
|---|---|
| 問いと背景 | 1 行 1 問い。答えで何が決まるか |
| 範囲と前提 | 調べた範囲と範囲外、前提 |
| 方法と期間 | 時間枠、環境、読んだ範囲。打ち切った物も書く |
| 観点と重み、候補 | 比較のときだけ。足切りは点に混ぜない。候補には現状のままを含める |
| 比較表と根拠 | 観点と候補の表。根拠の列に出典の番号 |
| 考察 | 任意。事実と分けた解釈 |
| 未確認と限界 | 試していないことと、結論への影響 |
| 結論と推奨 | 問いごとの答え、確信度（高・中・低）、推奨が変わる条件、次の一歩（担当と期限） |
| 出典 | 番号、題名、発行元、URL か場所、一次・二次、参照日 |

確信度は、出典が 2 系統以上で一致すれば高、1 系統なら中、推測なら低とする。Web の中身は変わるか消えるので、出典の表には参照日の列を置く。

## 6. ポストモーテムの形

ポストモーテムは、障害から学んで仕組みを直すための文書で、人を責めない。SRE の障害の記録（`skills/sre/templates/incident.md`）は当日の短い記録で、復旧のあとに書くのがここのポストモーテムである。時系列は事実だけを、対策は担当と期限つきで書く。

| 節 | 中身 |
|---|---|
| 文書情報 | 発生日、重大度、状態、著者（役職）、所有者、レビュー者、会議日 |
| 要約 | 何が起き、どれだけ影響し、どう直したかを 2〜4 文で |
| 影響 | 数字で。推定なら推定と書く |
| 背景と用語、経緯 | 社外や他チームが読むなら必須。障害の前にあったこと |
| 検知、対応と復旧 | 誰がどう気づいたか、検知までの時間、復旧までの時間 |
| タイムライン | 表。時間帯（JST か UTC）を宣言し、事実と根拠だけ |
| 根本原因と引き金 | 引き金、根本原因、寄与要因（複数） |
| 教訓 | うまくいったこと、いかなかったこと、幸運だったこと |
| 再発防止の対策 | 表。対策、優先度、担当（1 人）、期限、追跡先、状態 |
| やらないと決めた対策、外向けの文面、参考資料 | 任意。顧客に影響があれば外向けの文面は必須 |

人名ではなく役職で書き、「〜すべきだった」「〜できたはず」の反事実を書かない。「注意する」「周知する」だけの対策は人の注意に頼るので、仕組みか手順に落とす。

## 7. 要件定義書の形

要件定義書は、何を作るかを決める人と作る人の間の約束である。1 要件 1 文で、測れる受け入れ基準と検証方法を付け、作り方は書かない。要件の表には ID・優先度・受け入れ基準か要求値・検証方法の列を置く。

| 節 | 中身 |
|---|---|
| 文書情報 | 対象、決める人、作成者と確認者、状態、準拠、版 |
| 目的と背景、ゴールと管理指標 | 困りごとと数値の目標。測り方と測る時期 |
| 利害関係者と決める人、用語定義 | 誰が何を決めるか。3 回以上使う語 |
| 範囲と対象外、前提と制約 | 対象外には理由。制約には由来（組織・法令・連携先） |
| 業務要件 | 現行と新業務、業務量と時期 |
| 機能要件 | 「条件のとき、システムは応答する」の 1 文。異常時、根拠、優先度、受け入れ基準、検証方法 |
| 非機能要件 | 非機能要求グレード 2018 の大項目 A〜F。要求値と検証方法 |
| 移行・運用・教育・テストの要件、受け入れ基準と検証方法 | 作る物以外に要ること。試験・実演・検査・解析のどれで確かめるか |
| 追跡表、未決事項、保留 | 業務要件から試験までの対応。担当と期限。次の版の候補 |

優先度は Must・Should・Could・Won't（必須・重要・あれば良い・今回はやらない）で書く。要件の文に「など」「適切に」「速やかに」「十分な」「可能な限り」のような測れない語を使わない。

## 8. 仕様書の形

仕様書は、何を作るかと、なぜその形かを決める人と作る人が共有する文書である。利用者と場面、目標とやらないこと、振る舞いの詳細を先に置き、作り方と代替案を後ろに置く。2026-11-06 の型の仕様書も、検査は通す。7 つの節は、完成の条件・全体像・将来の変化・実装の進め方・やらないこと・未確定・確認事項である。

| 節 | 中身 |
|---|---|
| 3 行の要約、文書情報 | 何の仕様か、完成の条件、次にすること。状態、著者と審査者、関連、版 |
| 背景と範囲、利用者と場面 | 困りごとと範囲。誰がどの場面で使うか |
| 目標とやらないこと | 数値の目標。やらないことには理由 |
| 全体像 | 文脈図と読み方。変わる部品を括弧で示す |
| 振る舞いの詳細 | ID ごとに入力・処理・出力・異常時 |
| 外部との境目、データ、品質の数値 | 相手と向きと形、失敗したとき。型と保持期間と個人情報か。p95 の応答時間 |
| 完成の条件と確かめ方 | ID ごとに確かめ方と検証の方法 |
| 設計の概要と制約、代替案と却下の理由 | 作り方の要点。却下の理由とやらない場合の影響 |
| 横断事項、実装の進め方と移行、将来の変化 | 安全・個人情報・観測・費用。段階と戻し方。採用の理由にしない |
| 未確定、用語、確認事項、改版履歴 | 問いに担当と期限。社長に判断してほしいこと |

代替案の表には却下の理由の列、未確定の表には担当と期限の列を置く。将来の変化は書いてよいが、いま作る形の採用の理由にはしない。

## 9. 検査が見るもの

機械で見られる決まりは `tools/lib/check_doc.py` にあり、`skills/documents/scripts/shape-check.sh` が文体と文の運びの検査と束ねる。種類は表題の先頭「種類:」か末尾の語で決め、相手の形で表題に種類が無いときは `--kind` で渡す。

| 種類 | 必須の節（見出しに含む語） | 表の列と語の決まり |
|---|---|---|
| 手順書 | 目的、前提、手順、確認、切り戻し、記録 | 手順の節に番号の無い段落が 3 行以上あれば落ちる。操作ごとに期待結果 |
| 運用設計書 | 方針、体制、運用項目、監視、バックアップ、障害、変更 | 文書情報の表が表題の直下にある |
| 調査報告書 | 問い、範囲、方法、比較、未確認、結論、出典 | 比較の表に根拠か出典の列。出典の表に参照日の列。結論に確信度と「推奨が変わる条件」 |
| ポストモーテム | 要約、影響、検知、対応、タイムライン、原因、教訓、対策 | 影響に数字。タイムラインは表で時間帯を宣言。対策の表に担当・期限・優先度・状態の列で、担当と期限は空にしない。注意や周知だけの対策と、反事実の語で落ちる |
| 要件定義書 | 目的、指標、範囲、対象外、前提、制約、業務要件、機能要件、非機能要件、受け入れ、追跡、未決 | 機能要件と非機能要件の表に ID・優先度・受け入れ基準（か要求値）・検証方法の列。ID は空にせず重複させない。優先度は Must・Should・Could・Won't。要件の文に曖昧語が無い。未決の表に担当と期限 |
| 仕様書 | 背景、利用者、目標、やらないこと、振る舞い、完成の条件、代替案、横断、未確定（か 2026-11-06 の 7 語） | 新しい型のとき、代替案の表に却下の理由の列、未確定の表に担当と期限の列 |

`--theirs` を付けると、必須の節と文書情報の検査を外し、相手の節構成を正本にする。文体の検査（禁則語、一文 60 字、調の混在）と文の運びの検査は、どの種類でも外れない。
