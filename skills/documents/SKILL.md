# documents — 6 種類の文書を、相手の形で書く

文書が「手順書らしくない」「仕様書らしくない」原因は、節の名前ではなく中身の形にある。操作と理由が混ざる・比較表のセルに解釈が入る・対策に担当と期限が無い・相手の文体と違う、の 4 つを順に消す。文の決まりは `.company/rules/writing.md`、節の決まりは `.company/rules/documents.md` が受け持ち、ここは文書の種類ごとの形だけを見る。

## いつ使うか

社長か役割が、手順書・運用設計書・調査報告書・ポストモーテム・要件定義書・仕様書を書くとき。写した先で「手順をまとめて」「調べて」「振り返りを書いて」「要件を決めて」「仕様にして」と頼まれたとき。出来た文書がその種類らしくないと言われたとき。Runbook（当番の手順書）と障害の当日の短い記録は `skills/sre/SKILL.md` の受け持ちで、ここでは触らない。

## 先に読むもの

- `.company/rules/documents.md`（資料の型と、冒頭の「相手の形を正本にする」）と `.company/rules/writing.md`（文の決まり）。他のプロジェクトでは `tmp/.company/rules/` の同じ名前のファイル。
- `references/shapes.md`（6 種類の形、2 つの型の違い、相手の形の探し方、検査が見るもの）。
- `templates/` の雛形 6 本（procedure、ops-design、investigation、postmortem、requirements、specification）。
- `examples/` の完成例 6 本。手順書と運用設計書は My-Lab の作業、ポストモーテム・要件定義書・仕様書は見本アプリ orders-admin、調査報告書は雛形の調査そのものを題材にしている。

## 判断の観点

1. 相手に既存の同種の文書があるか。あれば、その節構成と文体（常体かですます調か）を正本にする。無いときだけ雛形を使う。
2. どの型か。調査報告書と仕様書は判断する人が読む資料の型で、3 行の要約から始める。残る 4 種類は現場の文書の型で、文書情報の表から始め、読み手の説明の節を置かない。
3. 読み手は、どの行を見ながら手を動かすか。手順書は操作の行だけで最後まで進めるか。運用設計書は運用項目一覧の欄が埋まっているか。
4. 事実と解釈が分かれているか。調査報告書の比較表とポストモーテムのタイムラインは事実と根拠だけにし、解釈は考察・結論・教訓に置く。
5. 測れるか。要件の受け入れ基準・仕様書の完成の条件・調査報告書の確信度・対策の担当と期限が、数値と名前で書いてあるか。
6. 無い数字を書いていないか。測っていない件数・時間・割合は未確認か未決に置く。

## 手順

1. 相手の形を探す。作業中のプロジェクトの docs や mkdocs、README の下で、同じ種類の文書を 1 本開く。探すのはターミナルの ls と cat で、作業中のプロジェクトの外は見ない。終わりの印: 節の名前と文体を書き留めた。無ければ「無い」と書き留めた。
2. 型を選ぶ。6 種類のどれかを決め、題を資料の型なら「種類: 件名」、現場の文書の型なら「対象 件名 種類」の形にする。終わりの印: 題から種類が読める。
3. 雛形を写す。相手の形があればその節構成に、無ければ `templates/` の雛形を `tmp/flow/<件名>/` に写す。置き場の印（〈〉）を全部埋めるか、行ごと消す。終わりの印: 印が残っていない。
4. 書く。手順書は操作を番号付きの 1 行に、コマンドをその直下に、期待結果を続きの行に書く。運用設計書は運用項目一覧を先に埋める。調査報告書は結論と確信度を先に書き、比較表と出典で支える。ポストモーテムは時系列を事実だけで書き、対策に担当と期限を入れる。要件定義書は 1 要件 1 文で、優先度と受け入れ基準と検証方法を列に埋める。仕様書は利用者と目標と振る舞いを書いてから、代替案の却下の理由を書く。終わりの印: 雛形の表の欄が全部埋まるか「未確定」になっている。
5. 検査する。`scripts/shape-check.sh <ファイル>` を回す（型の検査、文体の検査、文の運びの検査を束ねる）。相手の形で表題に種類が無いときは `--kind 種類`、相手の節構成を正本にするときは `--theirs` を付ける。終わりの印: `RESULT: PASS shape-check`。FAIL は直して回し直す。
6. 読み手テストを受ける。別コンテキストに文書だけを渡し、その種類の問いに答えさせる。手順書は「最初の操作は何か」「失敗したらどこへ進むか」を問う。調査報告書は「結論と確信度は何か」、ポストモーテムは「引き金と最初の対策は何か」を問う。要件定義書と仕様書は「完成の条件はどう確かめるか」を問う。終わりの印: 問いの全部に文書の文だけで正答。

## 出力と受け渡し

| 成果物 | 置き場 | 渡す先 |
|---|---|---|
| 手順書 | `tmp/flow/<件名>/procedure.md`。相手の置き場があれば、そこへ写す提案を添える | 作業する人、秘書（門） |
| 運用設計書 | `tmp/flow/<件名>/ops-design.md` | 運用の担当、秘書 |
| 調査報告書 | `tmp/flow/<件名>/investigation.md` | 社長（秘書の門を通して） |
| ポストモーテム | `tmp/flow/<件名>/postmortem.md`。対策は Issue 文の案を添える | SRE 役、秘書 |
| 要件定義書 | `tmp/flow/<件名>/requirements.md` | 社長（決める人）、作る役割 |
| 仕様書 | `tmp/flow/<件名>/specification.md` | 社長（確認事項の判断）、作る役割 |

## 禁止

- 相手に既存の同種の文書があるのに、自分の型と文体を押し付ける。
- 手順の節に理由や背景の段落を書く。コマンドと期待結果を付録に離す。
- 比較表のセルに解釈を書く。確信度と推奨が変わる条件を書かずに結論を出す。
- ポストモーテムで人を名指しする。「〜すべきだった」の反事実と、「注意する」「周知する」だけの対策を書く。
- 要件の文に「など」「適切に」「速やかに」のような測れない語を使う。優先度を高・中・低で書く。
- 「この節では」「この節で分かること」で節を始める。口座・合言葉・入れ物のような言い換えで、現場の語（アカウント、パスワード、Issue）を壊す。 <!-- ja-ok -->
- 測っていない数値を書く。実行していない手順を「確認した」と書く。
- 承認のない commit・push・Issue と PR の作成。文書を書いたところで止まり、パスを報告する。

## 提出前の確認

1. `scripts/shape-check.sh <ファイル>` が PASS（型の検査、文体の検査、文の運びの検査）。
2. 相手の形を探した記録が、文書情報の「様式」か要約の 3 行目にある（「既存の〇〇に合わせた」か「無いので雛形を使った」）。
3. 種類ごとの芯が埋まっている。手順書は操作の行だけで最後まで進める。運用設計書は運用項目一覧の欄が埋まっているか「未確定」。調査報告書は確信度と推奨が変わる条件がある。ポストモーテムは対策に担当と期限がある。要件定義書は優先度と受け入れ基準と検証方法が全行にある。仕様書は代替案に却下の理由がある。
4. 別コンテキストの読み手テストに正答。
