# Issue の型と、節ごとの根拠

> **3 行でわかる要約**
> 1. Issue は、その件を初めて見る人が質問せずに着手できるように書く文書で、節の順と中身をここで決めます。
> 2. 型の土台は Mozilla のバグ報告の指針と GitHub の Issue フォームで、節ごとに「なぜ要るか」を表にしました。
> 3. 書くときは `templates/issue-template.md` を使い、`scripts/issue-check.sh` で機械の検査を通します。

## 1. 読み手

読み手は 3 種類います。どの読み手も、質問せずに着手できることを目標にします。

| 読み手 | 知っていること | 知らないこと |
|---|---|---|
| 新人 | 画面の名前 | 作りと経緯 |
| 運用の担当 | 利用者の困りごと | コードの場所 |
| 他のチームの人 | 自分のチームの作り | この件の背景と、やらないことの線 |

## 2. 節の順と根拠

節は読み手が上から読む順に並べます。分からなくなった所で読むのをやめるので、要約と背景を先に置きます。

| 節 | 書くこと | 根拠 |
|---|---|---|
| 題名 | 起きている問題を 1 行で。直し方ではなく症状を書く。60 字以内 | Mozilla（要約は解決策ではなく問題を書く） |
| 3 行の要約 | 何の Issue か、どうなれば終わりか、着手する人が最初にすること | 読み手は上から読み、分からない所で止まる |
| 背景と目的 | 誰が、どの場面で、何に困っているか。件数や時間の数字と出どころ。なぜ今か | 目的が無いと、直し方の良し悪しを決められない |
| 起きていること | 不具合なら、番号つきの再現手順、期待する結果、実際の結果、再現の頻度、環境。機能なら、今の動きと望む動き | Mozilla（再現手順が最も大事。事実と推測を分ける） |
| 完了の条件 | 1 行 1 条件で、全行に確認方法 | 確認できない条件では、終わりを決められない |
| やらないこと | 範囲の外と理由 | 書かないと、読み手は好きに広げる |
| 手がかり | 関係する画面・ファイル・ログ・過去の決定。見当は「見当（未確認）」と印を付ける | 着手する人が探す時間を減らす。事実と推測を混ぜない |
| 用語 | 初出の専門語の言い換え | 新人でも読める |
| 未確定 | 決まっていないことと、誰がいつ決めるか | 決まっていないことを決まったように書かない |

## 3. 守ること

1 つの Issue には 1 つの問題だけを書きます。2 つ混ざると、片方が終わっても閉じられず、議論も混ざります。優先度は書きません。優先は社長が決めるので、Issue に書くと判断を先取りします。数字は出どころと日付を添え、架空なら「架空」と書きます。

## 4. GitHub のフォーム

My-Lab の `.github/ISSUE_TEMPLATE/` には、不具合・機能・調査の 3 つのフォームと、白紙の Issue を出させない設定（`config.yml`）があります。フォームの必須欄（`validations` の `required: true`）で、再現手順と完了の条件を空のまま出せないようにしています。`templates/` の `*.yml` は同じ中身の写しで、`evals/run.sh` が食い違いを見ます。他のプロジェクトでは、リポジトリの中にフォームを置けないので、`templates/issue-template.md` で本文を書き、GitHub に貼ります。
