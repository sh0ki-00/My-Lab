# 問い合わせの数・性能予算・移行・観測

> **3 行でわかる要約**
> 1. 件数が増えても遅くならない API と、止めても壊れない移行と、たどれるログを決めるための参考資料です。
> 2. 問い合わせの数は件数によらず一定にし、性能予算は p99 と測定点で書き、移行は意味を変えない足し算にします。
> 3. 計画を書いたら、`scripts/query-count-check.sh` で問い合わせの数と p99 を測り、計画の表に実測を写してください。

## 問い合わせの数

一覧の行ごとに問い合わせを出すと、行の数だけ時間が延びます。これを N+1（一覧の行ごとに問い合わせを出すこと）と呼び、作りません。

| 場面 | 決め |
|---|---|
| 行に付く名前（担当など） | JOIN で同じ SQL に入れる |
| 行ごとの集計（明細の数など） | 1 回の GROUP BY で数え、行に結ぶ |
| 件数と群ごとの件数 | 行と別に、1〜2 回の SQL で数える |
| 一括の書き込み | `IN (…)` で 1 回の条件つき UPDATE を先に流し、書けた行を RETURNING で受ける。書けなかった行はあとで 1 回読んで分ける。履歴は `INSERT … SELECT` で 1 回 |
| 溜まり続ける行（済の行、履歴） | 状態だけの索引でなめない。今日の分は時刻の索引で引き、別の索引で引く部分は UNION ALL で足す。溜まった行を足したデータで測る |
| 確かめ方 | 件数の違うデータ（例: 24 件と 400 件）で、1 要求の SQL を数える。同じ数なら PASS |

## 性能予算

予算は p99（遅い方から 1% の応答時間）で書きます。平均は遅い 1% を隠すので使いません。予算には測定点を必ず添えます。

| 書くこと | 例 |
|---|---|
| 操作 | `GET /v1/orders` |
| p99 の予算 | 300ms |
| 測定点 | サーバーが要求を受けてから応答を書き終えるまで |
| 打ち切り | 予算とは別。API 自身の打ち切りは画面の打ち切りより短くする |
| 実測 | 回数と機械と日付を添える。見本の値を本番の根拠にしない |

## 移行

移行は、どの段階で止めても旧と新の両方が動く順にします。最初に考えるのは、列や印の意味を変えずに済む形です。新しい形が要るなら、API が読むときに作れないかを先に見ます。例えば、取消の印 is_cancelled から契約の status の cancelled を作ります。

印を 2 つ持って写す移行は、最後の手にします。旧い書き手が動くかぎり、写しと戻しの窓が版と段と書き手の組み合わせごとに開くからです。旧い書き手は 1 つとは限らず、取り消しと戻しのほかに決済の通知や受注もあります。見本の注文一覧では、印を移す案で審査の重大が 9 件出て、印を移さない案に替えました。

| 決め | 中身 |
|---|---|
| 正は 1 つ | 正の印は 1 つのまま、意味を変えない。新しい API は読むときに新しい形を作り、書くときも同じ印を書く |
| 旧い書き手は変えない | 旧い API の文は直さない。新しい API の書き込みは、正の印を条件に入れる（例: 出荷指示は is_cancelled = 0 の行だけ） |
| 足し算だけ | 列・表・トリガー・索引を足す。既存の行を書き直さず、表をなめて数えない。消すのは別の計画にする |
| 足した物は外さない | 移行が終わるまで、足した列・トリガー・索引を戻しで外さない。戻すのは新しい API の機能フラグと書き込みだけにする。外したあいだに旧い書き手が書く窓が、第 9・10 回の審査の重大を全部生んだ |
| 旧い書き手を変えない形 | 旧い書き手の文を断らない（断りうる外部キーと CHECK は足さない）。列の型を前提にしない（トリガーは行と値を字にして比べ、読めない値は書き込みを止めない側に倒す）。旧い書き手の値を書き換えない。旧い書き手の全部の文を、足した物がある本物の DB で流して確かめる |
| 分からなければ null | 足した列の値（取り消しの人と時刻など）は、正の印が変わった取引でトリガーが書いた値だけにする。印を戻せば消し、立て直せばその取引の値に替える。素通りの書き手を作らないよう、PostgreSQL のトリガーは ENABLE ALWAYS にする（replica の取り込みでも動く）。行の xmin とは比べない。セーブポイントの中の書き込みと表の写し直しで xmin が変わり、正しい値まで消える |
| 書き手は列の権限でも探す | RLS を有効にする前の確かめは、表の単位の権限（has_table_privilege）だけでなく、列の単位の権限（has_any_column_privilege）でも書き手を探す。列の権限だけの旧い書き手に方針が無いと、その UPDATE はエラーにならず黙って 0 行になる |
| ロックを短く | 表の定義を変える文は 1 つの取引に入れ、`SET LOCAL lock_timeout` を取引の中だけに置く（セッションに残すと、あとの索引作りが打ち切られる）。既定値も制約も無い列を足す。索引は取引の外の `CREATE INDEX CONCURRENTLY` で 1 つずつ作り、前に lock_timeout と statement_timeout を 0 に戻す。足してよい制約は NOT VALID で足し、別の時に VALIDATE する |
| 列を名前で読む | `SELECT *` を使わない。列が増減すると、準備済みの文が "cached plan must not change result type" で失敗する部品がある |
| 段ごとに書く | 止めたときの状態、戻し方、確かめ方。戻し方は新しい API を止める形にし、足した物を外さない。消す前の写しからは戻さない |

計画には「版と段の表」を置きます。行は、その表を書きうる全部の書き手と API の版です。開いたままの古い画面が呼ぶ版と、決済や受注のようなほかの書き手も入れます。列は移行の段と、新しい API を戻したあとの状態で、升ごとに書き込みを受けるか断るかと、その理由を書きます。旧い API を止める段があるなら、その API が書いていた移り（例: 決済待ちから出荷可）の書き手を先に移す段も要ります。

表の升は試験で回し、旧と新の書き手が同じ行に代わる代わる書く順を全部流します。1 手ごとに、移行の前の DB（全部を旧い API の文で流した DB）と同じ結果かを比べます。あわせて 4 つを確かめます。(a) 取り消した行が出荷されない。(b) 取り消しが黙って外れない。(c) 戻した取り消しが黙って残らない。(d) 決済などの移りが、移行の前と同じに起きる。わざと穴を入れた写しでは、この試験が落ちることも確かめます。穴の例は、印を条件に持たない版、別の印で決める版、status を動かす版です。

足した段ごとに、旧い API の書き手を全部流し、書けた行の数と旧い列の値が移行の前と同じことも確かめます。本番の移行の文は、消す文、行を書き直す文、数える文が無いことを検査で見ます。

## 観測

ログは 1 要求 1 行の要約にします。1 行に、追跡番号・パスの型・状態番号・エラーコード・時間・SQL の数・利用者の id を入れます。氏名、住所、検索の語、鍵、冪等キーの値は書きません。メソッドのように要求から来る語は、決まった語に置き換えてから書きます。鍵を確かめる前に断る要求でも、相手の文字列をそのまま書かせません。

呼び手が W3C Trace Context（追跡の見出しの国際規格）の `traceparent` を送れば、その番号を追跡番号にします。無ければ API が作ります。エラーの本文と応答の見出しに同じ番号を入れます。

| 項目 | 例 |
|---|---|
| traceId | 32 桁の 16 進数 |
| route | `/v1/orders/{orderId}`（実際の番号は入れない） |
| status、code | 404、ORDER_NOT_FOUND |
| durMs、sql | 0.41、5 |
| user、role | u-takagi、operator |
