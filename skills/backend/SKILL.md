# backend — 契約・認可・冪等・移行を決めた計画を書き、検査で守られた API にする

## いつ使うか

秘書の受付票で依頼の型が「実装（API）」か「設計（データ）」のとき。画面仕様と実装計画を受けて API を作るとき、既存の API の契約を変えるとき、表を足すか既存のデータを移すときにも使う。画面の見た目と文言はデザイナー、網と鍵の置き場はインフラが決めるので、このスキルでは決めない。

## 先に読むもの

- `.company/backend/CLAUDE.md`（ペルソナ）と `.company/DELIVERY.md`。
- 画面仕様 `tmp/flow/<件名>/screen-spec.md`（エラーの表と権限の表）と、実装計画 `tmp/flow/<件名>/frontend-plan.md`（API への要望とタイムアウト）。無ければ秘書に戻す。
- インフラの環境と秘密の置き場、セキュリティの脅威モデル、SRE の SLO。無ければ仮置きにし、未確定に書く。
- `references/contract-and-errors.md`（契約が先、壊す変更、エラーの 4 点、起点の送り、冪等キーと一括の書き込み）。
- `references/authz-and-exfil.md`（資源 1 件ごとの認可、404 で隠す、流出経路の 6 つの出口と図の描き方）。
- `references/data-performance-ops.md`（N+1 を作らない、p99 と測定点、意味を変えない足し算の移行と版と段の表、1 要求 1 行のログ）。
- `templates/`（計画の雛形 `backend-plan.md`、契約の雛形 `openapi-contract.json`）、`examples/`（注文一覧の計画、契約の 1 版目と壊した 2 版目）。見本の API は `samples/api/`。

## 判断の観点

1. 契約が先か。入出力の形とエラーの表を JSON で決めてから作る。壊すなら版を分ける。世界の基準は Google の API 設計の指針（AIP-180、AIP-158）。
2. 認可は資源 1 件ごとにサーバーで判定しているか。範囲は鍵から決め、他人の資源は 404 で隠す。基準は OWASP API Security Top 10 の API1。
3. 同じ要求には同じ答えか。書き込みは冪等キー、競合は版番号。一括は検証で分け、書く行は全件か無し。
4. 件数が増えても回数と時間は増えないか。問い合わせの数を件数の違うデータで数え、予算は p99 と測定点で書く。
5. どの段階で止めても壊れないか。足すのが先、消すのは別のリリース。どの出口からもデータが出ないか。

## 手順

1. 入力を読む。画面仕様のエラー表と権限表、実装計画の API への要望とタイムアウト。終わりの印: 要望の数とエラーコードの数を言える。
2. 契約を書く。`templates/openapi-contract.json` を写し、操作・応答の欄・エラー・冪等キー・起点の送りを決める。終わりの印: `scripts/contract-check.sh <契約.json>` が PASS。
3. 要望に 1 件ずつ答える。断るなら理由と代わりの案を書く。エラーは画面仕様のコードと 1 対 1 にし、画面仕様に無いコードはデザイナーに文を頼む。
4. 認可を表にする。役割ごとに読む・書く・判定の場所。他人の資源は 404、役割の無い書き込みは 403。
5. 冪等と同時の更新を決める。キーの保持の期間、同じキーで違う内容の 422、一括の書き込みの単位。
6. データと移行を決める。時刻は UTC、金額は整数。正の印や列の意味は変えず、新しい形は読むときに作る。移行は意味を変えない足し算にし、段ごとに止めたとき・戻し方・確かめ方を書く。足した物は移行のあいだ外さず、戻すのは新しい API の機能フラグと書き込みだけにする。足す物は旧い書き手の文を断らず、列の型を前提にしない。大きい表の索引は取引の外の CONCURRENTLY、制約は NOT VALID と VALIDATE に分ける。本番の形の SQL は本物の DB で流して確かめる。書き手と版を行に、段を列にした版と段の表を置き、旧と新の書き手が代わる代わる書く試験で升を回す。
7. 問い合わせの計画と性能予算を書く。操作ごとの SQL の数、p99 の予算と測定点、API 自身の打ち切り。
8. 観測を書く。1 要求 1 行の要約の項目、追跡番号、ログに書かないもの。
9. 流出経路の図と 6 つの出口の表を書く。出口ごとに、この API での経路・守り・確認方法。終わりの印: 6 行が埋まった。
10. テストと段階と未確定を書く。受け入れ条件 1 件にテスト 1 本。段階ごとに止めたときの状態。
11. 検査を通す。`scripts/backend-plan-check.sh <計画>` と `tools/check-file.sh <計画>`。秘書が `editor` で読み手テスト（バックエンドからは呼べない）。
12. 承認のあとで実装する。契約のとおりに作り、段階ごとに `scripts/query-count-check.sh --plan <計画> --app <実装>` を回す。測った問い合わせの数と p99 を計画の表に写す。
13. 契約を変えるときは、`scripts/contract-check.sh <旧版> <新版>` で壊す変更が 0 件であることを確かめる。

## 出力と受け渡し

| 成果物 | 置き場 | 渡す先 |
|---|---|---|
| 設計と実装計画 | `tmp/flow/<件名>/backend-plan.md` | 秘書（承認伺いに契約・段階・未確定の 3 点を写す） |
| 契約（OpenAPI 3.1 の JSON） | `tmp/flow/<件名>/openapi.json` | フロントエンド（エラー表、起点と `since` の使い方） |
| エラーの表と、画面仕様に無いコード | 計画のエラーの節 | デザイナー（文の決め） |
| 待ち受けの網、DB の利用者の権限、移行の時間帯、写しの消す日 | 計画の流出経路と移行の節 | インフラ |
| 要約のログの項目、p99 の予算、打ち切り | 計画の観測と性能予算の節 | SRE |
| 6 つの出口の守りと確認方法 | 計画の流出経路の節 | セキュリティ（審査の依頼） |

秘書には、要約 10 行以内・未解決の対立・承認が要る判断の 3 つを `skills/secretary/templates/reply-from-role.md` の型で返す。承認が要るのは、契約を壊す変更、移行の時間帯、予算の値である。

## 禁止

- 契約を決めずに実装を始める。版を分けずに契約を壊す。エラーの 4 点を欠く応答。
- 上限のない OFFSET の一覧。画面側だけの認可。他人の資源に 403 を返して存在を教える。
- 冪等キーの無い書き込み。どこまで書けたか分からない部分成功の一括更新。
- 1 件ずつの問い合わせ。打ち切りの無い外部呼び出し。トランザクションの中の外部呼び出し。
- UTC 以外での保存。小数の金額。足すことと消すことを同じリリースに入れる移行。
- 測定点の無い性能目標。測っていない数値を実測と書く。氏名・住所・検索の語・鍵をログに書く。
- 本物の鍵をファイルに書く。他の役割の判断を代行する。承認のない commit・push・Issue と PR の作成、本番への操作、データの削除と移行の実行。

## 提出前の確認

1. `scripts/contract-check.sh <契約.json>` が PASS。変えた契約は `<旧版> <新版>` の比較も PASS。
2. `scripts/backend-plan-check.sh <計画>` と `tools/check-file.sh <計画>` が PASS。
3. `scripts/query-count-check.sh --plan <計画> --app <実装>` が PASS（SQL の数が件数で増えない、p99 が予算内）。出力の MEASURE の行を計画に写した。
4. 流出経路の表の 6 行に、守りと確認方法がある。確認方法の試験が実在して通る。
5. 秘書に返す 3 つ（要約・未解決の対立・承認が要る判断）が `skills/secretary/scripts/reply-check.sh` を通る。
