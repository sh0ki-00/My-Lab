# 地図の決まり: 6 つの節、根拠、鮮度、追記の候補

> **3 行でわかる要約**
> 1. キャッチアップ（作業の前に掴むこと）で残す地図の形と、検査の決まりをまとめた資料です。
> 2. 地図は入口の 1 枚と 6 つの節で、表の全部の行に根拠を付け、根拠のファイルが変わった節は「古い」として落ちます。
> 3. 書く前には 1〜4 節を読み、検査が落ちたら 7 節で決まりの名前を引いてください。

## 1. 置き場とファイル

地図は移した先の tmp/catchup/ に置きます。プロジェクトの中のファイルなので、別のセッションからも同じ物を読めます。Claude Code と Cursor のどちらからでも読めます。

| ファイル | 中身 | 書く人 |
|---|---|---|
| index.md | 入口の 1 枚。80 行以内で、全部の節への案内を持つ | キャッチアップのセッション |
| stack.md、team.md、entrypoints.md、vocabulary.md、traps.md | 5 つの節。テンプレートは `templates/` にある | キャッチアップのセッション |
| data.md | データの節。backend の `skills/backend/templates/data-dictionary.md` を写す | キャッチアップのセッション |
| inbox.md | 追記の候補。ふつうのセッションが 1 行ずつ足す | ふつうのセッションと、更新のセッション |
| facts.jsonl | 事実の記録。F-001 の形の番号とハッシュ値 | catchup-facts.sh だけ |
| schema.json、queries.jsonl | スキーマの写しと、クエリの記録 | キャッチアップのセッションが回した backend のデータの道具だけ。調査のセッションの記録は tmp/flow/<件名>/ に置く |
| stamp.json | 地図を作った commit、根拠のファイルのハッシュ値、走査したファイルの一覧 | map-check.sh --stamp だけ |

移した先の tmp/ は、deploy.sh が git の無視の対象にしています。地図はプロジェクトの commit に入らず、手元のセッションどうしで共有します。

## 2. 6 つの節

節は 6 つで、1 つの節を 1 つのファイルに書きます。節の名前は、入口の節の表の 1 列目と、各ファイルの表題（# の行）に、そのまま書きます。

| 節 | ファイル | 中身 | 根拠の取り方 |
|---|---|---|---|
| 構成と動かし方 | stack.md | 言語と版とフレームワーク、DB、起動とテストのコマンド、回した結果 | 設定ファイルの行と、事実の番号 |
| 開発の形 | team.md | 個人かチームか、既存の決まりと文書の型、既存の UI の部品 | commit の作者の数（事実の番号）と、設定と文書の行 |
| 入口 | entrypoints.md | 画面、API、定時の処理、外とのつながり | ルート（URL やコマンドの名前と処理の組）の定義から機械で拾った事実の番号と、コードの行 |
| データ | data.md | データの辞書、書き込む処理、食い違い、語彙と基準の数字、読んだ範囲、クエリの記録 | 読み取りだけのクエリの番号 |
| 語彙 | vocabulary.md | 依頼者の語と、コードとデータの名前の対応。「売上」のような数の定義 | コードの行か、聞き取りの日付 |
| 罠 | traps.md | 名前と中身が合わない所、動いていない経路、同じ処理の重複 | 参照を示すコードの行と、データの記録 |

データの節の決まりは、backend のスキルが持ちます。掴む順と罠の 10 の型は `skills/backend/references/existing-data.md` にあり、検査は `skills/backend/scripts/data-dictionary-check.sh` です。map-check.sh は、データの節にこの検査を呼びます。

開発の形の「個人かチームか」は、catchup-facts.sh が決めた値をそのまま写します。この 1 年の commit の作者が 2 人以上ならチーム、1 人なら個人です。0 人なら全期間の作者で決め、それも 0 人なら不明と書きます。

## 3. 入口の 1 枚

入口の 1 枚は、常時ルールの読む順が指す、ただ 1 つのファイルです。ふつうのセッションはこれを読んで、次に開く節を決めます。

| 部分 | 決まり |
|---|---|
| 長さ | 80 行以内。詳しい中身は節のファイルに書く |
| 冒頭の表 | 項目と内容の表に、commit と作った日と DB の読み取りの許可（許可した日と相手と範囲か、「無い」）を必ず書く。環境の名前と根拠の記録も書く |
| 節の案内 | 節とファイルの列を持つ表に、6 つの節と追記の候補の 7 行を置き、ファイルの列にリンクを書く |
| 先に知っておく罠 | 調査で数を取り違えやすい罠を、5 行までにする |
| 基準の数字 | 依頼者がふだん見ている数を、地図の定義で数え直した結果。「一致」の行は、画面の値と数えた値が等しく、どちらもクエリの番号の結果にある数（画面の値は依頼の文でもよい） |
| 使い方 | ふつうのセッションがすることを 3 行で書く |

節の案内のリンクは、地図の置き場からの相対のパスにします。完成例は、データの節に backend のスキルの完成例を指しています。

## 4. 根拠

節のファイルにある表は、全部の行に根拠を 1 つ以上書きます。主張は表の行にだけ書き、散文には節の要点と読み方だけを書きます。散文の主張は、検査が根拠を照らせないからです。

| 根拠 | 書き方の例 | 検査が見ること |
|---|---|---|
| ファイルと行 | app/orders.py:12、app/orders.py:12-20、app/orders.py の 12 行、Dockerfile:1、.python-version:1。空白を含むパスは `` `app/管理 画面.py`:3 `` | ファイルがプロジェクトの直下の中にあり、行がファイルの行数の内にある。直下の外を指す根拠（../ など）は落とす |
| クエリの番号 | Q-018 | queries.jsonl にその番号があり、ハッシュ値が合う |
| 事実の番号 | F-005 | facts.jsonl にその番号があり、ハッシュ値が合う。その事実の根拠のファイルも鮮度の対象にする |
| 聞き取り | 聞き取り（2026-11-26、依頼者） | 日付がある。語彙の節で、依頼者に確かめた行に使う |

事実とクエリの記録は道具だけが書き、AI は手で書きません。記録の番号は前の続きで振られるので、更新のあとも古い番号の行は読めます。

推測で埋めた行は書きません。分からないことは「不明」か「未確認」と書き、探した事実の番号を根拠に付けます。

## 5. 鮮度

鮮度は、根拠のファイルの中身と、走査したファイルの増減で決めます。地図を作り終えたら、map-check.sh --stamp で今の commit と根拠のファイルのハッシュ値と走査したファイルの一覧を記録します。記録の置き場は stamp.json です。

| 検査 | 落とすもの | 決まりの名前 |
|---|---|---|
| 中身の比べ | 地図を作った commit のあとに中身が変わったか、消えた根拠のファイル。その節を古いとする | 古い |
| ファイルの増減 | 走査したファイルの一覧と比べて、増えたか消えたファイル。コードは入口・データ・構成と動かし方、マイグレーションと SQL はデータ、設定とコマンドは構成と動かし方と入口、文書と UI の部品は開発の形を古いとする | 古い |
| 入口の 1 枚 | 入口の表が根拠に挙げたファイルも、節と同じく比べる。SECTION の行は「入口の 1 枚」 | 古い |
| 記録の漏れ | stamp.json に無い根拠のファイルか、走査したファイルの一覧。節を書き足したのに記録し直していない | 鮮度 |
| commit の比べ | 入口の commit と、stamp.json の commit が違う | 鮮度 |
| 記録の書き換え | stamp.json のハッシュ値が合わない | 鮮度 |

map-check.sh は、節ごとに SECTION の行で新しいか古いかを出します。--fresh を付けると鮮度だけを見るので、ふつうのセッションは、これで触る節が古いかを確かめます。

DB の形の鮮度は、map-check.sh では見ません。提出前に手で回す検査が、DB を待たずに済むようにするためです。DB の形は、調査の前に schema-snapshot.sh の --expect-hash で比べます。事実の記録の数（作者の数やファイルの数）は、記録を書いた時刻の値です。

## 6. 追記の候補

ふつうのセッションは、地図との食い違いに気づいたら inbox.md の表に 1 行足します。地図の本体は書き換えません。

| 列 | 書くこと |
|---|---|
| 日付 | 気づいた日（2026-11-27 の形） |
| 節 | 6 つの節の名前のどれか |
| 気づいたこと | 地図と何が違ったか |
| 根拠 | ファイルと行、クエリの番号、事実の番号、tmp/ の文書のどれか |
| 状態 | 足すときは未処理。更新のセッションが、反映済みか見送りに変える |

map-check.sh は、未処理の行の数を INFO の行で出します。未処理があっても落としませんが、更新のセッションは未処理の行を全部片付けてから記録します。

## 7. 検査の決まりの一覧

map-check.sh が落とす決まりは、次の表のとおりです。FAIL の行では、角括弧で囲んだ名前で出ます。

| 決まりの名前 | 落とすもの |
|---|---|
| 無い | 地図の置き場が無い |
| 使い方 | 地図が tmp/catchup に無いのに、--root でプロジェクトの直下を渡していない |
| 入口 | index.md が無い。冒頭の表に commit か作った日か DB の読み取りの許可が無い。commit が 16 進でも「無い」でもない。許可に日付も「無い」も無い |
| 入口の長さ | index.md が 80 行を超える |
| 節の案内 | 6 つの節か追記の候補への案内が無い。案内のファイルが無い |
| 節の表題 | 節のファイルの表題に、節の名前が無い |
| テンプレートの穴 | 角括弧の穴が埋まっていない |
| 根拠 | 表の行に根拠が無い。節に表の行が無い |
| 根拠の実在 | 根拠のファイルか行か、記録の番号が無い。根拠が直下の外を指す |
| 基準の数字 | 入口の基準の数字の表で「一致」と書いたのに、値が違うか、出どころの数と合わない（C-5） |
| ハッシュ値 | 事実かクエリの記録が、道具の書いたあとに変わった |
| 記録の形 | 記録の行が JSON として読めない |
| データの節 | data-dictionary-check.sh がデータの節を落とした。その FAIL の行をそのまま添える |
| 道具が無い | データの節を見る data-dictionary-check.sh が無い |
| 追記の候補 | 表が無い。日付、節、状態、根拠のどれかが決まりと違う |
| 鮮度、古い | 5 節の表のとおり |

data-dictionary-check.sh は、データの節でも表の行ごとに根拠を見ます。書き込む処理の網羅と、基準の数字の一致も見ます。決まりの名前は `skills/backend/references/existing-data.md` の「調査の決まりと検査」にあります。

git の無いプロジェクトでは、入口の commit を「無い」と書きます。データの節の commit の欄には、「git なし」と作った時刻と根拠のハッシュ値を書きます。根拠のハッシュ値は、データの節の表が根拠に挙げたファイルの中身から作る値です。

| 場面 | すること | 検査が落とすもの |
|---|---|---|
| データの節を書き終えた | data-dictionary-check.sh --evidence-hash に data.md と --root を渡し、VALUE の行をデータの節の commit の欄に写す | 「git なし」なのに、作った時刻か根拠のハッシュ値が無い（鮮度） |
| 根拠のファイルが変わった | データの節の古い行を読み直して直し、--evidence-hash で値を出し直す | 根拠のファイルから作り直した値が、欄の値と合わない（鮮度） |
| git の作業ツリーで書いた | 「git なし」ではなく、git rev-parse --short HEAD の値を書く | 直下が git の作業ツリーなのに「git なし」と書いた（鮮度） |

検査は、根拠のファイルから値を作り直して比べます。そのため、git の無いプロジェクトでも、データの節の古さを検査が見つけます。ただ、根拠に挙げていないファイルの変化は、この値に入りません。ファイルの増減は、5 節の走査したファイルの一覧で見ます。

検査が間違っていると思ったときも、検査を緩めて通しません。地図の行を直すか、検査の持ち主に直す案を渡します。
