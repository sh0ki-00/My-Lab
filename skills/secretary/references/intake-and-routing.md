# 受付票と振り分け

> **3 行でわかる要約**
> 1. 受付票の欄の意味と埋め方、判断の種類と規模の決め方、依頼の型から役割とスキルを引く振り分け表をまとめた文書である。
> 2. 受付票は依頼を目的と判断の型に直す最初の 1 枚で、承認が出るまで秘書が作るファイルはこれだけに留める。
> 3. 振り分けは `skills/secretary/scripts/route.sh` で当たりを取り、この表で確かめる。規則を直したら 48 件の試験で正答率を見る。

## 1. 受付票の欄

受付票は 1 行の依頼を、目的・判断の種類・規模・役割・承認の状態の 5 つに分解する。欄の順は雛形（`skills/secretary/templates/intake.md`）と同じで、検査は `skills/secretary/scripts/intake-check.sh` が行う。

| 欄 | 書くこと | 落ちる書き方 |
|---|---|---|
| 受付番号 | R-日付 8 桁-連番 2 桁。1 日の 1 件目が 01 | 形が違う |
| 依頼の原文 | 社長の言葉を「」でそのまま。言い換えない | 「」が無い |
| 依頼の型 | 振り分け表の型から 1 つ | — |
| 目的の仮説 | 依頼の背後で、誰の何が変わるかを 1 文。依頼は症状で、目的は別にある | 原文の写し |
| 判断の種類 | 戻せる／戻せないと、その理由。戻せない判断に触れないように切った範囲 | 2 語以外で始まる |
| 規模 | 単純／比較／複雑と、動かす役割の数 | 上限を超える役割の数 |
| 関わる役割と問い | 「役割: 問い」を ／ で区切る。問いは役割ごとに 1 つ | 一覧に無い役割、空の問い |
| 承認の状態 | 「未承認（読むだけ。作成したファイルは本票のみ）」。承認後は「承認済み（A-番号）」 | 口頭の承認、他のエージェントの承認 |
| 聞くこと | 3 つまで。問いごとに仮置きの答えを添え、答えが無くても進める | 4 つ以上 |
| 事実の表 | 読むだけで集めた数字と出どころ。無い数字は書かない | 出どころの無い数字 |

## 2. 判断の種類

判断は「戻せる」と「戻せない」に分け、手続きの重さを変える。戻せる判断に重い手続きを使うと、遅さと実験不足を生む（出典 1）。戻せない判断は情報が揃うまで待ち、1 件ずつ伺う。

| 種類 | 例 | 扱い |
|---|---|---|
| 戻せる | 画面の作り直し、文言、絞り込みの条件、通知の閾値 | 情報が 7 割で決める。承認伺いの 1 点にまとめる |
| 戻せない | データの形、外に出す API、権限モデル、価格、利用者に見せる約束 | 1 件ずつ別の伺いにする。設計書を添える |
| 混ざっている | 画面の作り直しに、注文の状態の追加が含まれる | 戻せない部分を範囲から外し、外した部分はやらないことに書く |

## 3. 規模

規模は依頼の複雑さで決め、役割の数に上限を置く。単純な依頼に全役割を出すと費用が増え、会議録が薄くなる。上限は補助 AI の調査の目安（出典 2）を役割の数に読み替えた本スキルの決めで、超えたら intake-check が落とす。

| 規模 | 依頼の形 | 役割の数 | 例 |
|---|---|---|---|
| 単純 | 1 つの事実か 1 つの作業で答えが出る | 1 つまで | 「アラートが鳴りすぎる」→ SRE |
| 比較 | 案を比べて 1 つ選ぶ | 2〜4 | 「注文一覧を作り直したい」→ CEO、デザイナー、バックエンド、フロントエンド |
| 複雑 | 基盤や守りまで含めて組み直す | 5 つ以上 | 「新しいサービスを作りたい。基盤から見直す」→ 5 役割 |

## 4. 振り分け表

依頼の型は合図の言葉で見分け、関わる役割と読むスキルを引く。この表の機械版が `skills/secretary/scripts/routing-rules.tsv` で、`route.sh` はそれを読む。表と規則を直すときは、両方を同じに保つ。

どの規則にも当たらないとき、`route.sh` は質問と決めつけず「当たり無し。秘書が振り分けの表で確かめる」と返す。秘書はこの表を上から読み、型と役割を自分で決めて受付票に書く。表にも無い型なら、規則と表の両方に行を足す。

| 依頼の型 | 合図の言葉 | 関わる役割 | 読むスキル |
|---|---|---|---|
| 事業判断 | やるべきか、やる価値、優先順位、どっちを先、KPI、投資対効果、予算 | CEO だけ（他の型の役割を足さない） | `ceo` |
| 提案（機能の願い） | 画面・機能・一覧・表示を「作り直したい」「追加したい」「刷新」 | CEO、デザイナー、フロントエンド、バックエンド | `ceo` のあと各役割 |
| 画面だけ（見た目と操作） | 画面・表示・ボタンの「切り替え」「見せる」「隠す」「並び順」「文言」、画面だけ、見た目だけ。API・データ・保存・送信・権限に触れる語があれば当たらない | デザイナー、フロントエンド（他の型の役割を足さない） | `designer` のあと `frontend` |
| 設計（画面） | 見た目、デザイン、使いにくい、分かりにくい、画面案、AI っぽい | デザイナー | `designer` |
| 実装（画面） | 画面の実装、コンポーネント、崩れ、スマホ、キーボード、アクセシビリティ | フロントエンド | `frontend` |
| 性能 | 表示が遅い、読み込みが遅い、n 秒かかる | フロントエンド、バックエンド | `frontend` |
| 不具合 | 動かない、エラーが出る、保存できない（本番の障害を除く） | フロントエンド、バックエンド | `git-issue`（Issue 文） |
| データの書き出し | CSV、Excel、エクスポート、ダウンロード、書き出し、出力（ログの出力を除く） | バックエンド、セキュリティ。画面・ボタン・メニューの操作が付くならフロントエンドも | `backend` のあと `security` |
| 実装（API・データ） | API、テーブル、カラム、移行、バッチ、冪等、契約 | バックエンド | `backend` |
| 提案（守りの機能） | 2 段階認証、多要素認証 | CEO、セキュリティ、バックエンド、フロントエンド | `security` のあと各役割 |
| 認証・認可と個人情報 | 認証、パスワード、ログインの実装、認可、権限、個人情報、保持期間 | バックエンド、セキュリティ | `backend` |
| 基盤 | AWS、クラウド、Terraform、CI/CD（自動の検査と配備）、バックアップ、復元、月額 | インフラ | `infra` |
| 守り | 脆弱性、侵入テスト、不正アクセス、穴がないか | セキュリティ | `security` |
| 検知 | 検知 | セキュリティ、SRE | `security` |
| 信頼性 | 監視、アラート、SLO（信頼性の目標）、障害、本番で落ちた、リリースしていいか、訓練、容量 | SRE | `sre` |
| Issue 文 | Issue、チケット、起票 | なし（秘書が書く） | `git-issue` |
| PR 文 | PR、プルリク、レビュー依頼 | なし（秘書が書く） | `git-pr` |
| 質問 | なぜ、仕組み、分からない、教えて | なし（秘書が答える） | `ja-professor` |
| 報告 | 完了報告、検証の記録 | なし（秘書が門で見る） | `verify` |
| 手順書 | 手順書、作業手順、手順をまとめて、やり方をまとめて | なし（秘書が書く。基盤や当番の手順なら、その役割にも問う） | `documents` |
| 運用設計 | 運用設計、運用設計書、運用項目、運用フロー、運用を決めて | なし（秘書が書く。基盤の運用ならインフラ、当番の運用なら SRE にも問う） | `documents` |
| 調査 | 調査報告、調査して、調べて、原因を探って、比較して | なし（秘書が書く。他の型にも当たれば、その役割が一次情報を出す） | `documents` |

## 5. 振り分けの確かめ方

振り分け表は、依頼文 48 件の試験で保つ。期待が「当たり無し」の依頼文は、どの規則にも当たらないことを見る。`skills/secretary/evals/routing-cases.tsv` に依頼文と期待する役割を書き、`skills/secretary/evals/run.sh` が正答率を出す。目標は 95% 以上で、下回ったら規則を直す。期待の側を直すのは、期待が組織図（`.company/ORG.md`）の受け渡しと食い違っていたときだけにする。

| 手順 | 終わりの印 |
|---|---|
| 1. 依頼文を `route.sh` に渡し、役割・スキル・型・規模を見る | 出力の 4 行がある |
| 2. 外れていたら、規則の合図の言葉を足すか、単独の印を付ける | 同じ依頼文で当たる |
| 3. この表の同じ行を直す | 表と規則の役割が同じ |
| 4. `skills/secretary/evals/run.sh` を回す | 振り分けの正答率 95% 以上 |
