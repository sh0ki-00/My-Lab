# 図の決まり

図は飾りではなく、文章では伝わらない「関係」を伝える道具である。内容の型に合わない図は、文章より分かりにくい。
型を選び、要素を絞り、読み方を添える。記法は Mermaid（文字で図を描く記法）である。Claude Code・Cursor・GitHub のどれでも描画される書き方だけを使う。機械検査は `tools/check-mermaid.sh`、実際の描画は `tools/render-mermaid.mjs` が確かめる。

## 1. 原則

| 決まり | 具体的には |
|---|---|
| 1 図 1 メッセージ | 図を 1 文で言える。言えないなら 2 枚に分ける |
| 内容の型で選ぶ | 下の表に従う。表にない型は使わない |
| 要素は 12 個以内 | ノードが 12 個を超えたら、全体図と詳細図に分ける |
| 境界は subgraph で | 「守る範囲」「外部」「チーム」のような境界を箱にする |
| 色は使わない | 意味を持つときだけ使い、意味を凡例に書く |
| 直後に読み方 | 「左から右へ。点線は失敗時」のように 1〜2 文 |

## 2. 図の選び方

| 伝えたいこと | 使う図 | Mermaid の種類 |
|---|---|---|
| 手順、分岐、判断 | フローチャート | `flowchart` |
| 誰が誰に何を送るか | シーケンス図 | `sequenceDiagram` |
| データの持ち方 | ER 図 | `erDiagram` |
| 状態の移り変わり | 状態遷移図 | `stateDiagram-v2` |
| 部品の配置と境界 | 構成図 | `flowchart` と `subgraph` |
| 日程 | ガントチャート | `gantt` |
| 比較、位置づけ | 表 | Markdown の表 |

## 3. 書き方

- ノードの id は英数字だけ。表示名はラベルに書き、ラベルは引用符で囲む（`A["注文 API"]`）。
- `end` を id に使わない（予約語）。
- ラベルの中の括弧やコロンは、引用符で囲まないと描画が崩れる。
- 矢印の意味は 1 種類にするか、凡例を書く。
- 片方のツールでしか描画されない拡張記法を使わない。

## 4. 出す前

1. `tools/check-mermaid.sh <ファイル>` を通す。種類、引用符、id、`subgraph` と `end` の対応、ノード数。
2. `verify-all.sh` の実描画の検査が、全図を実際に描いて崩れがないことを確かめる。
3. 図を置いた節が、図ではなく導入の文から始まっていることを見る。
